# 量房后业务流程实现方案：建档 → 设计 → 报价 → 谈单 → 签约

> 适用范围：装得清小程序端（th4-decoboon-app）+ 后端（th4-decoboon）
> 起点：客户已完成现场量房（
> `Measure.status = completed`
> ）
> 终点：合同签署并生成唯一履约项目（
> `Project.status = preparing`
> ）
> 状态机以服务端为权威源，前端只提交动作后重新拉取，不本地维护流转。



***

## 0. 总览：一条主线、两套状态、五类角色

### 0.1 业务主线（销售五步 + 履约交接）



```
到店 → 跟进 → 量房 → 设计 → 报价 → 谈单 → 签约 → \\\[施工履约]

\&#x20;               ↑                     ↑

\&#x20;         本文起点              谈单是报价与签约之间的"临门一脚"
```

`SalesSteps` 组件固定五步：`到店 / 跟进 / 量房 / 设计 / 报价`；签约与履约由 `flow.vue` 的 "签约后业务流转" 区承接，不在销售步骤条内重复。

### 0.2 两套并行状态机（必须理解）



| 状态机        | 实体                    | 枚举（前端）                                                                                          | 推进权威                  |
| ---------- | --------------------- | ----------------------------------------------------------------------------------------------- | --------------------- |
| **客户主阶段**  | `Customer.stage`      | `intention → following → pendingMeasure → quote → sign → construction → done`（`lost` 旁路）        | 后端领域服务按动作自动迁移，前端只读展示  |
| **房屋状态**   | `Property.status`     | `pendingMeasure → measuring → measured → designing → quoted → contracted → serving → completed` | 同上，随业务动作推进            |
| **设计方案状态** | `DesignScheme.status` | `draft → ready → presented → selected`（`archived` 旁路）                                           | `design/scheme/build` |
| **报价状态**   | `Quote.status`        | `draft → submitted → accepted / rejected → superseded / converted`                              | `quote/update`        |
| **谈单状态**   | `TalkPlan.status`     | `draft → generated → published`（`archived`）                                                     | `design/talk/build`   |
| **合同状态**   | `Contract.status`     | `draft → pendingSign → signed → effective/active → changed → completed/settled`                 | `project/contract/*`  |
| **项目状态**   | `Project.status`      | `preparing → ongoing → accepting → finished → settled`                                          | 履约域，不在本文              |

**关键关系**：`Customer` 是销售主线；`Property` 是房屋维度（一客多房）；`DesignScheme / Quote / TalkPlan / Contract / Project` 都挂在 `customerId + propertyId` 上，按房屋维度隔离。

### 0.3 角色与可见域



| 角色      | 代码         | 在本流程中的职责                       | 数据范围    |
| ------- | ---------- | ------------------------------ | ------- |
| 业务员     | `marketer` | 到店 / 跟进 / 约量房 / 移交设计 / 催签约     | 自己名下客户  |
| 设计师     | `designer` | 量房纪要 / 设计诉求 / 方案 / 报价 / 谈单 PPT | 自己接手的房屋 |
| 项目经理    | `pm`       | 签约后履约（本流程终点处交接）                | 自己负责的项目 |
| 老板 / 店长 | `boss`     | 全企业可见，审批报价 / 合同变更              | 企业范围    |
| 客户      | `customer` | 接收谈单 PPT、确认报价、签合同、确认变更         | 仅本人     |

前端按 `session.role` 切换 API 前缀（如 `customer/customer/*` vs `project/manager/customer/*`），**服务端仍必须强制校验**，前端切换只是少打无权限请求。

## 1. 阶段一：量房后建档（量房完成 → 设计接手）

### 1.1 业务目标

量房完成不是终点，而是把 "模糊线索" 沉淀为**可设计、可报价、可追责**的结构化档案。必须在移交设计师前完成：



1. 房屋档案补全（地址、面积、户型、量房数据）

2. 量房纪要归档（现场照片、原始结构、尺寸、客户口述、设计师结论）

3. 客户画像补全（决策角色、预算、风格、入住时间、关注点）

4. **移交设计师**（handoff），触发 `Customer.stage → quote`、`Property.status → designing`

### 1.2 领域对象与字段



| 对象                 | 关键字段                                                                                                          | 说明                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------- | ---------------------- |
| `Customer`         | `name/phone/source/stage/owner/designer/budget/community/addr/area/remark`                                    | 客户主档                   |
| `CustomerPortrait` | `decisionRole/purpose/houseCondition/startWindow/style/eco/household/payment/concerns/competitor`             | 10 项营销画像，全部可空          |
| `Property`         | `propertyNo/community/building/roomNo/address/area/layout/status/designer`                                    | 房屋档案，一客多房              |
| `Measure`          | `designer/measureTime/status/sitePhotos/originalStructure/dimensions/customerRequirements/designerConclusion` | 量房纪要，挂在 `propertyId`   |
| `CustomerFollow`   | `way/content/nextFollowAt`                                                                                    | 跟进记录，量房后至少一条 "量房完成" 跟进 |

### 1.3 状态流转



```
Property.status:  measuring(量房中) ──saveMeasure(completed)──▶ measured(已量房)

Customer.stage:   pendingMeasure ──crmApi.measure()──▶ 保持 following/quote 待移交

\&#x20;                 following ──crmApi.handoff(designerId, propertyId)──▶ quote

Property.status:  measured ──handoff──▶ designing
```



* `crmApi.measure(customerId, measureAt, propertyId)`：记录量房完成时间，客户阶段推进。

* `crmApi.handoff(customerId, designerId, propertyId)`：**移交动作**，把 `designer` 写进客户与房屋，客户进入 `quote` 阶段，房屋进入 `designing`。

* 未移交前，设计师在自己的 "待接手" 列表看不到该客户。

### 1.4 API 链路



| 动作        | API                                 | 说明                              |
| --------- | ----------------------------------- | ------------------------------- |
| 补客户档案     | `customer/customer/save` / `update` | `writePayload` 组装，枚举转大写         |
| 补画像       | `customer/customer-portrait/save`   | 10 字段可空提交                       |
| 保存 / 编辑房屋 | `property/property/save` / `update` | `propertyId` 区分新建与更新            |
| 保存量房纪要    | `property/measure/save`             | 照片走 `fileApi.storagePath` 转存储路径 |
| 查量房记录     | `property/measure/page?propertyId=` | 一个房屋可多次复量                       |
| 写跟进       | `customer/customer-follow/save`     | 量房结论作为一条跟进                      |
| 移交设计师     | `customer/customer/handoff`         | 传 `designerId + propertyId`     |

### 1.5 界面交互逻辑

**客户详情页&#x20;**`customer/detail.vue`**&#x20;结构**（按 AGENTS.md §15）：



```
\\\[客户身份卡]  头像/姓名/电话/状态标签/顾问  \\\[打电话]\\\[加微信]

\\\[SalesSteps] 到店→跟进→量房→设计→报价   ← 当前节点高亮，唯一主 CTA

\\\[HouseCard]   房号/状态/面积/户型/折叠编号  \\\[录入量房] 或 \\\[查看量房]

\\\[客户信息]   来源/地址/营销进度/预算/画像

\\\[跟进记录]   时间/方式/内容/下次跟进        右侧 \\\[写跟进]

\\\[底部固定栏] \\\[写跟进：次按钮描边] \\\[下一步：主按钮实心]
```

**本阶段（量房刚完成，未移交）的交互细则**：



1. `SalesSteps.value = 'measure'`（当前节点 = 量房），下方唯一主 CTA = **"移交设计师"**。

2. `HouseCard` 显示 "已量房・128㎡"，右侧操作 = **"查看量房"**（已完成）或 **"补录量房"**（数据不全时）。

3. 点击 "查看量房" 进入 `measure-record.vue`：时间线展示历次量房，照片九宫格（`sitePhotos`），原始结构 / 尺寸 / 客户要求 / 设计师结论四段只读；右上角 "编辑" 补录。

4. **建档完整度检查（前端不做状态机，只做引导提示）**：

* 缺 `budget` / `community` / 至少 1 条跟进 → 在客户信息卡显示黄色提示条 "建议补充预算与小区"，点击直达编辑。

* 缺 `designer` → 底部主按钮禁用，文案 "请先选择设计师"。

1. 点击 "移交设计师"→ 弹出设计师选择器（按企业可分配设计师列表）→ 确认后 `crmApi.handoff` → `onShow` 自动重新 `crmApi.info`，客户阶段变为 `quote`，步骤条跳到 "设计"。

2. **三态**：客户详情用骨架屏；无房屋 → 空态插画 + "添加房屋" 按钮；加载失败 → "重试"。

### 1.6 关键边界规则



* **一客多房**：客户可有多套 `Property`，量房 / 设计 / 报价 / 合同全部按 `propertyId` 隔离；切换房屋时所有子列表（设计、报价、合同）用 `computed` 过滤，不重新请求。

* **禁止跨房屋串数据**：所有详情页必须按当前 `propertyId` 过滤（历史坑 FIX-001）。

* **量房可复量**：`measure/page` 返回多条，`latestMeasureAt` 只取最新；复量不删除旧记录，只新增 `status=completed`。

* **空值统一&#x20;**`—`：面积 / 预算 / 编号等缺失时显示 `—`，用 `$text-placeholder`，不写 "暂无 / 未填"。

## 2. 阶段二：设计（诉求归集 → 空间 → 方案与设计项）

### 2.1 业务目标

把量房纪要转化为**可报价、可谈单**的设计产物，包含三层：



1. **设计诉求**（`DesignRequirement`）：客户要什么、排斥什么，作为设计依据。

2. **空间清单**（`DesignSpace`）：每个房间的长 / 宽 / 高 / 面积 / 周长，是算量基础。

3. **设计方案**（`DesignScheme` + `DesignItem[]`）：方案封面 / CAD / 拆改图 / 各空间设计项（施工 / 主材 / 定制 / 电器 / 软装）。

### 2.2 领域对象



| 对象                  | 关键字段                                                                                                                                                |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DesignRequirement` | `customer/property/type(space)/spaceName/kind(demand/reject)/category/priority/status/title/detail/response`                                        |
| `DesignSpace`       | `type(6类)/name/length/width/height/area/perimeter/sort/remark/images`                                                                               |
| `DesignScheme`      | `no/name/customer/owner/version/style/status/area/coverUrl/cadUrl/originalPlanUrl/demolitionUrl/masonryUrl/optimizationUrl/sitePhotos/surveyPhotos` |
| `DesignItem`        | `space/type(6类)/category/name/brand/spec/unit/quantity/materialPrice/manualPrice/costPrice/pricingMode/amount/cost/formula/criterion/images`        |



* `DesignItemType`：`general综合 / construction施工 / material主材 / custom全屋定制 / appliance电器 / soft软装家具`

* `PricingMode`：`materialAndManual材料+人工 / materialOnly仅材料 / manualOnly仅人工 / fixedTotal固定总价`

### 2.3 状态流转



```
DesignScheme.status:

\&#x20; draft(设计中) ──design/scheme/build?status=Ready──▶ ready(待谈单)

\&#x20; ready ──build?status=Presented(已讲解)──▶ presented

\&#x20; presented ──build?status=Selected(客户已选中)──▶ selected

\&#x20; 任意 ──build?status=Archived──▶ archived(归档，不可再改)
```



* 设计师在方案编辑页维护草稿；"提交谈单"= build 到 `ready`。

* 现场讲解后由业务员 / 设计师手动标记 `presented`；客户选定方案后标记 `selected`。

* `selected` 是报价可提交的前置条件之一（业务上：未选定方案不报价）。

### 2.4 API 链路



| 动作        | API                                                                                |
| --------- | ---------------------------------------------------------------------------------- |
| 列诉求       | `design/requirement/page?customerId=`                                              |
| 存诉求       | `design/requirement/save`                                                          |
| 列方案       | `design/scheme/page?customerId=`（返回后走 `fileApi.grant('Design', id, paths)` 签名所有图片） |
| 新建 / 更新方案 | `design/scheme/save` / `update`（`designId` 有无区分新建）                                 |
| 推进方案状态    | \`design/scheme/build?designId=\&status=Ready                                      |
| 存空间       | `design/space/save`（`spaceId` 区分新建 / 更新）                                           |
| 删空间       | `design/space/delete?spaceId=`                                                     |
| 存设计项      | `design/item/save`（可挂 `catalogItemId/constructionId/materialId` 从字典带入价）            |
| 删设计项      | `design/item/delete?itemId=`                                                       |

**文件签名机制**：`designApi.scheme/info/schemes` 返回后统一调 `signScheme`，把 `coverUrl/cadUrl/originalPlanUrl/demolitionUrl/masonryUrl/optimizationUrl/sitePhotos/surveyPhotos/originalPlanImages/space.images/item.images` 全部走 `fileApi.grant('Design', designId, ...)` 换成临时可访问 URL，**禁止在前端写死 OSS 域名**。

### 2.5 界面交互逻辑

**入口**：客户详情 SalesSteps 当前节点 = 设计 → 主 CTA "进入设计" → `design/scheme.vue`（方案编辑）。

**方案编辑页&#x20;**`design/scheme.vue`**&#x20;分区**：



```
\\\[方案头]  封面图 / 方案名 / 风格 / 版本号 / 状态标签

\\\[基础文件] CAD / 原始结构图 / 拆改图 / 砌筑图 / 优化图（每个卡片：上传+预览+删除）

\\\[现场照片] sitePhotos / surveyPhotos（九宫格上传）

\\\[空间清单] DesignSpace 横向/纵向列表 → 点击进入空间编辑

\&#x20;         每空间：类型标签 / 名称 / 长×宽×高 / 面积 / 周长

\\\[设计项清单] 按 space 分组 → DesignItem 列表

\&#x20;         每项：名称 / 品牌规格 / 单位 / 数量 / 材料价+人工价 / 合计金额

\&#x20;         底部自动汇总：施工合计 / 主材合计 / 定制合计 / 总金额

\\\[底部固定栏] \\\[存草稿：次按钮] \\\[提交谈单：主按钮]
```

**关键交互**：



1. **诉求页&#x20;**`design/requirement.vue`：

* 顶部 Tab：`诉求(demand)` / `排斥点(reject)`。

* 表单字段：所属空间（可选 SpacePicker）、类别（功能 / 风格 / 材料 / 预算 / 工期 / 质量 / 其他）、优先级（高 / 中 / 低）、标题、详情。

* 已确认诉求显示 "已确认" 标签，未确认显示 "待客户确认"，点击可标记确认。

1. **空间编辑**：长 / 宽 / 高输入后，面积与周长用 `computed` 前端实时算（纯展示），保存时以后端为准；单位统一 `m² / m`。

2. **设计项编辑**：

* 从 `CatalogPicker`（主包公共组件）选字典项时，自动带 `materialPrice/manualPrice/costPrice/unit/spec`，设计师可覆盖。

* 金额 = `quantity × (materialPrice + manualPrice)`，`cost = quantity × costPrice`，前端实时算但**以保存后后端返回为准**。

* `pricingMode=fixedTotal` 时隐藏单价输入，只填总价。

1. **状态推进按钮**：

* `draft` → 主按钮 "提交谈单"（二次确认："提交后将生成谈单材料，确认方案已完整？"）。

* `ready` → 按钮变为 "标记已讲解"（业务员现场讲解后点）。

* `presented` → 按钮变为 "客户已选定"。

* `selected` → 方案锁定，编辑按钮降级为 "另存新版本"。

1. **多版本**：`DesignScheme.version` 自增，选定后新版本不影响旧版本，可归档。

### 2.6 关键边界规则



* **诉求与方案解耦**：诉求在客户级（`customerId`），方案在房屋级（`propertyId`）；一个客户可能为不同房屋做不同方案。

* **设计项必须挂空间**：`spaceId` 必选，否则报价按空间分组时无处归位。

* **图片懒加载 + 失败兜底**：所有 `images` 数组用 `lazy-load`，失败显示占位图。

* **返回刷新**：从诉求页 / 空间页返回方案编辑页用 `onShow` 重新 `scheme.info`，不依赖缓存。

## 3. 阶段三：报价（从设计项生成 → 客户确认）

### 3.1 业务目标

把设计项转化为**客户看得懂、能签字确认**的报价单。三种报价模式：



* `package` 套餐报价：选套餐模板，按面积 × 单价，含套餐项。

* `custom` 自定义报价：从设计项逐项带出，可增删改。

* `hybrid` 混合：套餐打底 + 个性化增项。

### 3.2 领域对象



| 对象               | 关键字段                                                                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Quote`          | `no/title/customer/property/design/packageTemplate/owner/mode/area/subtotal/amount/cost/discount/taxRate/taxAmount/status`                             |
| `QuoteItem`      | `name/type/category/space/brand/spec/unit/quantity/materialPrice/manualPrice/pricingMode/price/amount/cost/formula/included/discountAmount/components` |
| `QuoteGroup`     | `key/name/type/amount/cost/items[]`（按 region/construction/material/other 四种分组返回）                                                                       |
| `QuoteComponent` | `type/name/saleAmount/costAmount/formula`（套餐明细拆解）                                                                                                      |

### 3.3 状态流转



```
Quote.status:

\&#x20; draft ──quote/update?status=Submitted──▶ submitted(待客户确认)

\&#x20; submitted ──update?status=Accepted──▶ accepted(客户接受)

\&#x20; submitted ──update?status=Rejected──▶ rejected(已驳回，可改后重新 Submitted)

\&#x20; accepted ──生成合同──▶ converted(已转项目)

\&#x20; 新报价 ──旧报价自动──▶ superseded(已被替代)
```

**金额公式（服务端算，前端只读）**：



* `subtotal = Σ QuoteItem.amount`

* `amount = subtotal × discount + taxAmount`（`taxRate` 默认 0.05）

* `cost = Σ QuoteItem.cost`（毛利 = amount − cost，仅内部可见，客户端不返回 cost）

### 3.4 API 链路



| 动作        | API                                                                                        |
| --------- | ------------------------------------------------------------------------------------------ |
| 列报价       | `quote/page?customerId=&status=`（pm 走 `project/manager/quote/page`）                        |
| 报价详情      | `quote/info?quoteId=`（返回四种 group）                                                          |
| 新建报价      | `quote/save`（入参：`customerId/propertyId/designId/templateId/mode/area/discount`）            |
| 推进状态      | `quote/update?quoteId=&status=Draft\|Submitted\|Accepted\|Rejected\|Superseded\|Converted` |
| 报价列表（不分页） | `tradeApi.quotes({customerId, size:200})`                                                  |

**新建报价的两种来源**：



1. 从设计方案 "生成报价"：传 `designId`，后端把 `DesignItem[]` 拷贝为 `QuoteItem[]`。

2. 从套餐模板 "快速报价"：传 `templateId`，后端按 `area × price` 生成套餐项。

### 3.5 界面交互逻辑

**报价列表&#x20;**`quote/list.vue`：



* 卡片：报价单号 / 客户姓名 / 房屋 / 金额（橙色 `$text-price`）/ 状态标签 / 日期。

* 顶部筛选 Tab：全部 / 草稿 / 待确认 / 已接受 / 已驳回。

* 右下角 FAB"新建报价"→ 选择来源（从设计方案 / 从套餐模板）。

**报价详情&#x20;**`quote/detail.vue`**&#x20;结构**：



```
\\\[报价头]  单号 / 客户 / 房屋面积 / 模式标签 / 状态

\\\[金额摘要] 小计 / 折扣 / 税额 / 合计金额(大号字)  \\\[成本(内部可见)]

\\\[按空间分组 regionGroups]   每个空间：空间名 + 小计 + 展开项

\&#x20; └─ 每项：名称 / 品牌规格 / 单位×数量 / 材料+人工单价 / 合计

\\\[施工分组 constructionGroups]

\\\[主材分组 materialGroups]

\\\[其他 otherGroups]

\\\[备注/说明]

\\\[底部固定栏]

\&#x20; draft:     \\\[另存草稿 次按钮] \\\[提交客户确认 主按钮]

\&#x20; submitted: \\\[催办客户] \\\[驳回重报]

\&#x20; accepted:  \\\[生成合同 主按钮]

\&#x20; rejected:  \\\[修改后重新提交]
```

**关键交互**：



1. **金额展示**：价格用 `$accent-500`（暖木橙），数字 `font-variant-numeric: tabular-nums`；成本区块仅 `boss/designer` 可见，客户端请求不返回 `cost`。

2. **提交确认**：点击 "提交客户确认"→ `uni.showModal`："提交后客户将收到确认邀请，确认前可继续修改。" → `quote/update(Submitted)`。

3. **客户确认页**（`customer` 角色）：只看 `amount` 与清单，底部 \[接受报价] \[要求修改]；接受后 `quote/update(Accepted)`。

4. **驳回处理**：`rejected` 后可在 `quote/edit.vue` 修改数量 / 单价 / 增删项 → 重新 `Submitted`；旧 `submitted` 报价自动 `superseded`。

5. **防重复**：按钮 `loading` 态，请求返回前禁用；同客户同时只能有一份 `submitted` 报价。

### 3.6 关键边界规则



* **报价与设计方案绑定**：`Quote.design` 指向 `DesignScheme`，客户对报价的异议会回写到 `DesignRequirement.response`。

* **报价版本**：`Superseded` 状态的历史报价只读，可对比但不可转合同。

* **客户端金额脱敏**：客户角色调 `customer/contract/info` 等接口时，`cost` 字段后端不下发。

* **折扣上限**：低于成本价时后端拒绝，前端提交后弹错误 toast（不做前端拦截，信任后端）。

## 4. 阶段四：谈单（设计 + 报价 → 谈单 PPT → 现场讲解）

### 4.1 业务目标

谈单不是 "再讲一遍报价"，而是把**量房照片、设计思路、方案对比、投资概算、省钱点**串成一份客户能看懂的 PPT，现场逐页讲解。`TalkPlan` 是可版本化的谈单材料。

### 4.2 领域对象



| 对象            | 关键字段                                                                                                 |
| ------------- | ---------------------------------------------------------------------------------------------------- |
| `TalkPlan`    | `no/customer/property/design/quote/owner/title/version/status/coverUrl/outputUrl/builtAt/sections[]` |
| `TalkSection` | `type/title/subtitle/content/images/sort/visible`                                                    |

**20 种谈单章节**（`TalkSectionType`，固定顺序）：



```
cover 封面 → catalog 公司介绍 → community 楼盘 → requirement 客户诉求

→ sitePhoto 现场照片 → survey 量房 → surveyReport 量房报告

→ originalPlan 原始户型 → problem 现存问题 → demolition 拆改 → masonry 砌筑

→ optimization 户型优化 → roomDesign 各空间设计 → softDecor 软装

→ material 主材 → appliance 电器 → investment 投资概算 → saving 省钱点 → end 结尾
```

### 4.3 状态流转



```
TalkPlan.status:

\&#x20; draft(草稿) ──design/talk/build──▶ generated(已生成)

\&#x20; generated ──publish──▶ published(已发布，客户可见)

\&#x20; 任意 ──▶ archived
```



* `build` 是**全量重建**：从 `design` + `quote` 拉最新数据，按模板生成 `sections`，旧 sections 丢弃。

* `build` 入参 `designId`、`quoteId` 均必填（后端 `TalkContext.build` 校验：`quote == null` 直接报错，不允许无报价纯设计谈单）。

### 4.4 API 链路



| 动作     | API                                                                  |
| ------ | -------------------------------------------------------------------- |
| 列谈单材料  | `design/talk/page?designId=`                                         |
| 生成谈单材料 | `design/talk/build?designId=&quoteId=&talkId=`（`talkId` 传了就是基于旧版本重建） |
| 谈单详情   | `design/talk/info?talkId=`（图片走 `fileApi.grant('Talk', talkId, ...)`） |
| 更新谈单   | `design/talk/save`（改标题 / 描述 / 章节可见性）                                 |

### 4.5 界面交互逻辑

**谈单列表&#x20;**`design/list.vue`**&#x20;内 Tab"谈单 PPT"**：



* 卡片：封面缩略图 / 标题 / 版本 V1 / 状态 / 生成时间。

* 主 CTA"生成谈单材料"→ 选择报价（下拉选当前 `accepted` 或 `submitted` 的报价）→ `design/talk/build`。

**谈单详情&#x20;**`design/talk.vue`**&#x20;结构**：



```
\\\[顶部封面] coverUrl 全屏头图 + 标题 + 版本

\\\[章节纵向时间线] 按 sort 排列：

\&#x20; \\- 封面/公司介绍：纯展示

\&#x20; \\- 客户诉求：demand/reject 列表，高亮排斥点

\&#x20; \\- 现场照片/量房：照片九宫格 + 尺寸数据

\&#x20; \\- 原始户型/拆改/砌筑/优化：CAD/效果图横向滑动

\&#x20; \\- 各空间设计：roomDesign，每空间一屏

\&#x20; \\- 主材/电器：品牌+型号+参考价

\&#x20; \\- 投资概算：与报价 amount 一致，分区间展示

\&#x20; \\- 省钱点：saving 卡片

\\\[底部固定栏] \\\[预览输出 PDF outputUrl] \\\[标记已讲解]
```

**关键交互**：



1. **章节可见性**：`TalkSection.visible` 可在编辑页开关，隐藏的章节不进输出 PDF。

2. **图片横滑**：`roomDesign/material` 等多图章节用 `scroll-view scroll-x`，左右滑动，参考小红书图文比例。

3. **讲解联动**：讲解完点击 "标记已讲解"→ 同时把 `DesignScheme.status` 从 `ready` 推到 `presented`（一次动作，两个领域同步推进）。

4. **PDF 输出**：`outputUrl` 是后端渲染好的 PDF 临时 URL，点击 `uni.downloadFile` + `uni.openDocument`。

5. **客户可见**：`published` 状态下，客户端在 "我的设计" 里能看到这份 PPT；`draft/generated` 仅内部可见。

### 4.6 关键边界规则



* **谈单材料是派生视图，不是数据源头**：所有金额 / 项数从 `Quote` 实时读，不在 `TalkSection` 里存数字；改报价后必须重新 `build` 才能同步。

* **20 种章节是模板，不是必填**：`visible=false` 的章节可跳过，但 `cover/requirement/investment/end` 四个必选章节缺失时 `build` 应报错。

* **版本号**：每次 `build(talkId)` 自增版本，旧版本保留可回溯。

## 5. 阶段五：签约（接受报价 → 合同 → 项目生成）

### 5.1 业务目标

客户接受报价后，把 "报价" 升级为 "有法律效力、有收款节点、有履约计划" 的合同，并自动生成唯一项目。

### 5.2 领域对象



| 对象               | 关键字段                                                                                                                                                                                                                       |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Contract`       | `no/customer/projectId/quoteId/baselineAmount/currentAmount/amount/status/signedAt/startDate/planEndDate/paymentTerms/property/receivableCount/receivableAmount/receivedAmount/pendingChangeCount/signedCost/costComplete` |
| `Project`        | `no/name/address/community/area/layout/style/contractAmount/paidAmount/status/progress/startDate/planEndDate/customer/property/quote/designer/manager/marketer/supervisor/currentStageName`                                |
| `ContractChange` | `contractId/no/amount/type/reason/status/customerConfirmed/signatureUrl/evidenceItems/items[]`                                                                                                                             |

### 5.3 状态流转



```
Contract.status:

\&#x20; draft ──project/contract/save(quoteId)──▶ pendingSign(待签署)

\&#x20; pendingSign ──客户签署──▶ signed(已签署)

\&#x20; signed ──生效──▶ effective / active(履约中)

\&#x20; active ──变更审批+客户确认──▶ changed

\&#x20; active ──竣工验收──▶ completed

\&#x20; completed ──结算──▶ settled

\&#x20; 任意 ──▶ closed / terminated / void(终止/作废)

Project.status:

\&#x20; 合同生效自动创建 ──▶ preparing(待开工) ──▶ ongoing ──▶ accepting ──▶ finished ──▶ settled
```

**金额三态**：



* `baselineAmount` = 签约时报价 `amount`，**终身不变**（合同基线）。

* `currentAmount` = `baseline + Σ(已确认变更金额)`，随变更浮动。

* `amount` = 当前对外展示金额，前端统一读 `currentAmount || baselineAmount`。

### 5.4 API 链路



| 动作     | API                                                                                 |
| ------ | ----------------------------------------------------------------------------------- |
| 按报价查合同 | `project/contract/info?quoteId=`                                                    |
| 按项目查合同 | `project/contract/info?projectId=`（客户走 `customer/contract/info`）                    |
| 生成合同   | `project/contract/save?quoteId=&signedAt=&startDate=&planEndDate=&paymentTerms=`    |
| 更新合同   | `project/contract/update?contractId=&status=&startDate=&planEndDate=&paymentTerms=` |
| 列变更    | `project/contract-change/page?projectId=`                                           |
| 创建变更   | `project/contract-change/save`（增 / 减 / 换 / 量 / 价五类）                                 |
| 审批变更   | `project/contract-change/update?changeId=&approved=&conclusion=`                    |
| 客户确认变更 | `project/contract-change/customer-confirm?changeId=&signatureUrl=&evidenceImages=`  |

### 5.5 界面交互逻辑

**触发入口**：客户详情 SalesSteps 走完五步后，底部主 CTA = **"生成合同"**；报价详情 `accepted` 状态主 CTA 也是 "生成合同"。

**合同生成弹窗 / 页&#x20;**`project/create.vue`**（实际是合同参数确认）**：



```
\\\[合同头]  合同号(自动) / 客户 / 房屋

\\\[金额确认]  报价金额 = ¥XXX,XXX（基线，只读）

\\\[工期]  开工日期 picker / 计划竣工日期 picker

\\\[付款方式]  paymentTerms 文案框（如：3-4-2-1 三期）

\\\[收款计划预览]  receivableCount 节点列表（财务域展开，这里只读）

\\\[底部固定栏] \\\[保存草稿 次按钮] \\\[生成并送签 主按钮]
```

**合同详情（在&#x20;**`quote/detail.vue`**&#x20;底部或&#x20;**`project/detail.vue`**&#x20;内嵌合同卡）**：



```
\\\[合同状态条] pendingSign → signed → active → completed → settled

\\\[金额] 基线 ¥XX / 当前 ¥XX / 已收 ¥XX / 待收 ¥XX

\\\[工期] 开工 \\\~ 计划竣工 / 实际竣工

\\\[变更记录] pendingChangeCount > 0 时红色提示"有 N 条待确认变更"

\\\[底部]

\&#x20; pendingSign: \\\[客户签署]（电子签名，上传 signatureUrl）

\&#x20; signed:      \\\[确认生效]

\&#x20; active:      \\\[发起变更] \\\[查看项目]
```

**签署流程**：



1. 业务员点 "客户签署"→ 拉起客户端分享（微信会话卡片）或现场签名板。

2. 客户在签名板手写签名 → `fileApi.upload` 得到 `signatureUrl` → `project/contract/update(status=Signed, signedAt=now)`。

3. 后端在同一事务里：

* 写 `Contract.signedAt`；

* **自动创建&#x20;**`Project`（`projectId` 写回 `Contract.projectId`）；

* 把 `Customer.stage` 从 `sign` → `construction`；

* 把 `Property.status` 从 `contracted` → `serving`；

* 初始化项目阶段模板（拆除 / 水电 / 瓦工 / 木工 / 油漆 / 安装 / 竣工）。

1. 前端返回客户详情，`onShow` 重新拉取，SalesSteps 五步全部打勾，底部出现 "查看项目" 入口。

**变更流程（履约期，简要）**：



* 项目经理 / 设计师发起变更 → 选类型（add/remove/replace/quantity/price）→ 录 old/new 数量价格 → 传现场照片。

* 老板审批（`approved=true`）→ 推送给客户 → 客户电子签名确认 → `customerConfirmed=true` → `currentAmount` 重算。

* 变更金额超过合同额 ±10% 时强制老板二次审批（后端规则）。

### 5.6 关键边界规则



* **一报价一合同**：`quoteId` 唯一，同一报价重复生成合同返回已有合同（幂等）。

* **一合同一项目**：合同生效时 `Project` 自动创建，不允许手动新建项目。

* **合同基线不可改**：`baselineAmount` 永远 = 签约时报价金额，所有浮动走 `ContractChange`，不直接改合同金额。

* **签署不可逆**：`signed` 后 `Contract.status` 不可回退到 `draft`，作废走 `void`（需老板权限 + 备注原因）。

* **客户确认变更必须留痕**：`signatureUrl` + `evidenceImages` 双证据，缺一不可。

* **业务员在签约后只读**：`flow.vue` 明确 "业务员只读查看后续推进"，施工 / 收款 / 验收由项目经理和财务域接管。

## 7. 界面交互通用规范（每个页面必须遵守）



1. **三态**：loading 用骨架屏，empty 用插画 + 引导按钮，error 用说明 + 重试，禁止 "暂无数据" 裸文案。

2. **主 CTA 唯一**：一屏只能一个实心主按钮，其余用描边 / 文字按钮；底部固定栏 = 1 主 + 1 次。

3. **按钮防重**：请求中 `loading` 态禁用；破坏性操作（删除 / 作废 / 驳回）必须 `uni.showModal` 二次确认。

4. **金额**：`money()` 格式化，价格用 `$text-price`，数字 `tabular-nums`。

5. **空值**：统一 `—` + `$text-placeholder`。

6. **编号折叠**：长单号 `H1789…4323`，点击复制。

7. **图片**：`lazy-load`，上传后立即 `fileApi.storagePath` 转存储路径，展示前 `fileApi.grant` 签名。

8. **可点击性**：可点行必须有 `chevron-right` + `:active` 按压态，展示型胶囊不伪装按钮。

9. **路由**：所有跳转走 `P.*` 常量，分包跳转用绝对路径 `/subpackages/<domain>/pages/<page>`。

10. **图标**：统一 `JzIcon` 线性图标，禁止 emoji / 字符箭头。

## 10. 设计方案 / 报价 / 谈单间 / 谈单 PPT 关系详解

> 本章澄清四个易混概念。
>
> **系统里 "谈单间" 和 "谈单 PPT" 不是两张表，而是同一张&#x20;**
>
> `Talk`
>
> **&#x20;表的两个面**
>
> ：谈单间是单据记录（编号 / 版本 / 状态 / 关联指针），谈单 PPT 是它每次 build 时现算出来的 20 个章节 + 导出 PDF。

### 10.1 实体与职责



| 概念     | 实体（后端 / 前端）                      | 角色     | 存什么                                                                  | 不存什么                     |
| ------ | -------------------------------- | ------ | -------------------------------------------------------------------- | ------------------------ |
| 设计方案   | `Design` / `DesignScheme`        | 设计成果本体 | 空间清单、设计项（分项 / 数量 / 材料价 / 人工价）、CAD / 拆改 / 砌筑 / 优化图纸                   | 不存金额结论（金额在报价）            |
| 报价     | `Quote`                          | 金额结论本体 | 从 DesignItem 汇总的明细、折扣、税额、`amount`、`cost`                             | 不存设计图纸和客户诉求              |
| 谈单间    | `Talk`（主表）                       | 业务单据   | 编号 `no`、`version`、`status`、关联 `designId`+`quoteId`、`owner`、`builtAt` | **不存业务数据**，只是指针          |
| 谈单 PPT | `TalkSection[]`（后端 `@Transient`） | 内容投影   | 20 个章节的标题 / 文案 / 图片                                                  | **不持久化业务数字**，每次 build 现算 |

### 10.2 基数关系



```
Customer 1 ── N Design      （一个客户可做多套方案，主推方案可谈单即可生成 PPT）

Design   1 ── N Quote       （一份方案多版报价，旧版自动 superseded，有效版仅 1 份）

Design   1 ── N Talk        （一份方案多版谈单，每次 rebuild version+1）

Quote   1 ── 0..1 Talk      （Talk.quoteId 指向一份报价，build 时校验必须相等）
```

### 10.3 TalkContext.build 的三条硬校验（后端写死）



```
1\. design != null                                // 主推方案必须指定

2\. design.status ∈ {Ready, Presented, Selected}   // draft 方案不能谈单

3\. quote != null 且 quote.design.id == design.id   // 必须有本方案自己的报价
```

### 10.4 数据流（Talk 是派生视图，不是数据源）



```
DesignRequirement ──┐

DesignSpace ────────┤

DesignItem ────────┼──▶ TalkContext.build() ──▶ TalkSection\[20] ──▶ 导出 PDF(outputUrl)

Quote.subtotal ─────┤

Quote.discount ─────┘

Quote.taxAmount / amount
```

`TalkSection` 在后端是 `@Transient`，build 时先 `deleteByTalkId` 再全量 `saveAll`。改了设计项或报价金额后，Talk 里的 "各空间金额" 和 "投资概算" 不会自动变，必须重新 `buildTalk(designId, quoteId, talkId)` 让 version+1。

### 10.5 封板规则

`design/list.vue` 的 `locked` 逻辑：



```
locked = !!project || quotes.some(q => \['accepted','converted'].includes(q.status))
```

一旦报价 `accepted`/`converted` 或合同生效生成 `Project`：设计方案、报价、谈单 PPT 全部锁定，不能新建 / 编辑 /rebuild；后续任何调整只能走 `ContractChange`（合同变更单）。这保证 "客户签字的报价 = 合同基线"，与设计过程中的草稿彻底隔离。

### 10.6 一句话总结

> 设计方案是 "做什么"，报价是 "做这些要多少钱"，谈单间是 "把这两份材料汇编成给客户看的讲解稿（含版本）"，谈单 PPT 是谈单间每次 build 时从设计 + 报价现算出来的 20 页投影和 PDF。四者是 "源数据 → 金额结论 → 汇编单据 → 内容产物" 的单向流，Talk 不产生新业务数据，只负责组织表达。
