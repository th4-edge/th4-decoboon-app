# 装得清微信小程序 UI / UX 设计评审

- 评审日期：2026-10-28
- 评审对象：`th4-decoboon-app` 微信小程序
- 评审范围：员工端角色工作台、客户/项目/财务、报价与主材作业单、合同增减项、业主端首页与五槽导航
- 评审方式：`zhuangdeqing-ui-craft` 视觉门禁 + `dig-ui` review/anti-tells 透镜 + 当前源码 + Token + OCR + `qwen2.5vl:7b` 截图复核
- 评审结论：**方向正确，已有产品真实性；当前不建议以“视觉验收完成”或“可规模化推广”口径放行。**
- 状态：`PARTIAL_VISUAL_EVIDENCE`。当前源码可审，代表性历史截图可审；但缺少与 2026-10-28 当前代码一一对应的完整真机截图与七态证据。
- 代码变更：无。本文档为只读评审产物。

---

## 1. 一句话结论

装得清小程序已经不像通用 CRUD 模板：报价版本、合同增减项、主材作业单、成本未完整、业主确认与预览水印等设计，能看出真实装企业务。下一阶段不应继续“加卡片、加渐变、加装饰”，而应把 UI 从“信息都能看见”提升到“角色一眼知道先处理什么、数据是否可信、失败后怎么恢复”。

当前最重要的三个问题是：

1. **状态可信度不足**：部分页面在接口失败时仍显示 0、空态或“暂无”，会让用户把未知误判成真实业务结论。
2. **移动端信息负担偏重**：老板客户页、项目卡片、财务工作台等把过多指标同时放在一个视口中，扫描效率不稳定。
3. **可访问性未达 AA 口径**：关键灰色文字、语义色和部分小字号存在明确对比度与可读性风险。

## 4. 已经做得好的地方

### 4.1 角色不是装饰，而是实际影响工作台

- BOSS、店长、团队负责人、业务员、设计师、项目经理、财务和业主均有不同入口、数据范围与页面落点。
- 首页契约校验已覆盖 BOSS 内部能力超集、设计师五阶段队列、业主五槽导航等结构，而非只做视觉皮。
- 权限、门店范围、业主预览和隐藏内部成本等边界在代码中有明确处理。

### 4.2 关键业务链路有“产品真实性”

- 报价工作台不是普通列表：包含客户、项目、状态、金额、版本、提交时间、反馈时间、停留天数、调整次数与下一步。
- 报价详情有版本对比和“提交客户确认 / 报价推进中”等业务动作。
- 合同增减项有合同基线、明细、来源分项、工程量、金额试算、变更前后合同额和提交审批。
- 主材作业单有“设计师建单 → 项目经理测量确认 → 财务下单”的链路，并把成本待结算、待下单等状态放在对象身份附近。
- 成本不完整时不展示伪毛利，这和装得清的核心数据可信原则一致。

### 4.3 组件基础比旧版成熟

- 已有 `JzPageHeader`、`JzTag`、`JzEmpty`、`JzSkeleton`、`PageState`、`ListFooter`、`JzActionCard`、`JzTabBar` 等复用组件。
- 大多数页面已有下拉刷新、上拉加载、列表底部状态或重试入口。
- 金额普遍有统一格式化，多个关键数字使用 `font-variant-numeric: tabular-nums`。
- 动效多以按压、反馈和局部切换为主，没有看到大面积循环动画。

### 4.4 业主端独立子品牌是正确方向

- 业主端使用纸张、森林绿、苔绿和铜色 Token，与员工工作台区分，符合“业主不是内部员工”的产品关系。
- “我的家、当前阶段、待确认验收、我家的记录、服务团队、最近进展”这套叙事比通用九宫格更接近业主心智。
- 预览水印和只读横幅体现了内部预览的安全边界。

## 5. 关键问题与建议

## P0-1：未知数据被显示成 0 或空态，破坏“同源同口径”

### 现象

1. 财务工作台首次加载或加载失败时，`summary` 为 `null`，但统计卡通过 `|| 0` 产出 0；风险待办与最近流水则直接落入“暂无”空态。页面没有全页加载骨架或明确失败面。
   - 证据：`src/pages/finance/index.vue:74-107`
   - 证据：`src/pages/finance/index.vue:199-239`
2. 主材作业单列表加载失败只弹出 Toast，随后 `loading=false`，模板会显示“还没有主材下单作业单”。
   - 证据：`src/subpackages/project/pages/material-sheet.vue:55-98`
3. 主材作业单详情加载失败后只弹 Toast，随后 `sheet` 为空，页面显示“作业单不存在或无权访问”，把网络失败、接口失败和真实无权限混成一个语义。
   - 证据：`src/subpackages/project/pages/material-sheet-detail.vue:162-181`
   - 证据：`src/subpackages/project/pages/material-sheet-detail.vue:306-311`
4. 业主首页在 `journey` 尚未加载或加载失败时，记录区仍可能渲染“待更新”，时间线先渲染空态，加载/失败提示被放在页面尾部。
   - 证据：`src/components/owner/OwnerHome.vue:207-215`
   - 证据：`src/components/owner/OwnerHome.vue:253-276`

### 影响

- 用户会把“接口没有返回”理解为“业务真的是 0”或“没有单据”。
- 财务数字尤其危险：0 余额、0 待收、0 支出会直接改变经营判断。
- 这违背“未知显示暂不可确认，不用 0、空数组或本地常量伪装事实”的产品原则。

### 建议

- 为异步页面统一定义 `loading / ready / empty / error / no-permission / partial` 六类数据状态。
- 加载态保留页面结构骨架；失败态保留页面身份和范围，显示“数据暂不可确认”及重试；无权限态明确角色边界，不复用“无数据”。
- 财务、成本和金额指标在数据未就绪时只显示“暂不可确认”或“—”，禁止 `|| 0`。
- 对已有缓存的后台刷新，可以继续显示旧数据，但必须标注“数据截至 HH:mm，本次刷新失败”。

## P0-2：当前版本缺少可信的渲染证据，不能宣称 UI 验收完成

### 现象

- 现有可用的代表性截图时间集中在 2026-10-08 至 2026-10-21。
- 当前 App 工作区存在大量未提交改动，且业主首页源码已使用 `OwnerHome` 新结构。
- 历史业主截图中出现了“当前岗位 · 启动引导 / 岗位启动”等员工引导内容；当前源码已把员工与业主分支拆开，但尚无与当前结构对应的新截图。
- 因此，旧截图不能证明当前版本已经通过视觉、状态和真机验收。

### 影响

- 无法确认当前员工首页、老板客户工作区、项目卡片和财务工作台的真实视觉结果。
- 无法确认旧截图中的信息噪声、遮挡、字号和层级问题是否已随源码更新被修复。
- 只能给出“源码 + 历史截图”的评审，不能给出“当前版本验收通过”。

### 建议

- 对核心页面重新采一组当前版本证据：至少 iPhone SE/小屏、iPhone 15 Pro、Android 360×800 三档。
- 每页至少覆盖：正常、加载、空、失败、无权限、长内容、极端值。
- 截图必须与提交 SHA、构建版本、测试账号角色、项目范围和截图时间绑定。
- 在证据完成前，评审状态只能写“产品验证中”，不要写“UI 已验收”。

## P1-1：可访问性 AA 目前不成立

### 对比度

按 Token 计算：

| 组合 | 对比度 | 判断 |
|---|---:|---|
| `$jzb-text-3 #778390` / 白底 | 3.86:1 | 普通小字不达 4.5:1 |
| `$jzb-text-3 #778390` / 页面底色 `#F4F7F8` | 3.59:1 | 普通小字不达 4.5:1 |
| `$jzb-primary-dark #0E8A7D` / 白底 | 4.24:1 | 普通文字略低于 4.5:1 |
| 白色文字 / `$jzb-primary #16A394` | 3.13:1 | 普通按钮文字存在风险 |
| `$jzb-success #07A35A` / 白底 | 3.28:1 | 不适合作为小号正文语义色 |
| `$jzb-warning #E67E22` / 白底 | 2.85:1 | 不适合作为小号正文语义色 |
| `$owner-muted-2 #85928D` / 纸色 `#F4F1E9` | 2.87:1 | 业主元信息对比不足 |
| `$owner-muted #60716B` / 纸色 | 4.57:1 | 基本可用，但仍需真实渲染复核 |

`$jzb-text-3` 在 `.vue/.scss` 中约有 954 处引用，风险不是个别页面，而是系统级 Token 问题。

### 字号

- `$jzb-font-xs` 为 `22rpx`，在 375px 视口约 11px。
- 代码中还大量存在 `20rpx`、`19rpx`、`18rpx`，约 9–10px；`JzTabBar` 标签也是 `20rpx`。
- 这会让“次要信息”在实际使用中变成难读信息，尤其是财务金额说明、项目元信息、状态时间和业主档案摘要。

### 可交互语义

- 代码中约有 1151 个 `@tap`，但只有 393 个显式 `<button>`。大量卡片、文字和图标用 `view` 承载点击。
- 显式 `aria-label` 只有 3 处；47 个 `<image>` 标签没有显式 `aria-label`。
- 这不等于所有交互都不可用，但说明屏幕阅读器、长按菜单、hover/active 可发现性没有系统性覆盖。

### 建议

- 将普通辅助文字从 `$jzb-text-3` 提升到至少 4.5:1；状态语义色拆分“语义底色”和“语义文字色”，不要用同一个高饱和色承担小号正文。
- 正文建议不低于 `26–30rpx`；说明与元数据不低于 `24rpx`；仅角标、头像字母等可使用 `22rpx`。
- 所有图片补充可理解的 `aria-label`；图标动作优先使用 `button` 或 `role="button"` + `aria-label`。
- 触控目标保持至少 44px 等效热区；文字动作通过 padding 扩大命中区。
- 颜色不能单独表达状态，继续保留文字、图标和位置三重编码。

## P1-2：移动端卡片“信息全但不轻”，扫描效率不稳定

### 员工首页

- `src/pages/index/index.vue` 模板中出现 26 个 `jz-card` 引用，虽然并非同一角色全部同时显示，但角色首页仍是身份卡、绩效卡、快捷入口、专业工作台、材料卡、关注项目、经营动态等多组模块叠加。
- 首屏可能先展示身份和引导，再展示经营结论；对老板来说，“今天最该处理什么”可能不是第一眼最强者。

### BOSS 客户页

- 默认采用 `172rpx` 负责人侧栏 + 客户面板的双栏结构，且需要同时承载指标、搜索、门店筛选、阶段筛选、跟进筛选和客户卡片。
- “放大客户区”是一个有效的补救动作，但用户要先理解界面，才能进入更舒服的工作状态。
- 证据：`src/pages/customer/list.vue:795-835`

### 项目列表

- 单个 BOSS 项目卡同时放：项目身份、地址/面积、项目经理/设计师、来源标签、状态标签、风险原因、合同额、已收、回款率、回款进度、施工阶段、施工进度、计划完工、逾期天数、成本、毛利、毛利率、下一步和进入处理。
- 这是“全部信息都在一张卡里”，不是“按决策分层”。在手机上可能出现一屏只能看一张项目卡。
- 证据：`src/pages/project/list.vue:455-540`

### 建议

- 定义三种移动列表密度：
  - **队列行**：对象名 + 当前状态 + 责任人 + 一个风险/金额 + 下一步；
  - **经营卡**：结论 + 两个关键事实 + 一个主行动；
  - **详情页**：完整金额、成本、历史和数据来源。
- 项目卡首层只保留“风险/阶段/回款/下一步”，成本、毛利、人员、来源和计划日期移入展开区。
- BOSS 客户页在小屏默认进入“客户区聚焦”模式，负责人分组改为可收起筛选，而不是默认长期占据左侧宽度。
- 首页按角色建立“首屏优先级”，而不是所有角色都堆同样的模块。

## P1-3：事务表单的主行动容易被折在首屏之外

### 现象

- `src/subpackages/finance/pages/entry.vue` 使用普通文档流放置提交按钮，按钮位于提示说明之后。
- 2026-10-10 的财务登记截图中，首屏可见 8 个字段和底部说明，但没有看到主提交按钮。
- 证据：`src/subpackages/finance/pages/entry.vue:859-868`

### 影响

- 用户完成表单后需要额外滚动才能发现提交动作。
- 长表单中“保存/提交”与风险提示的关系不稳定，也容易与软键盘、安全区叠加。

### 建议

- 长表单统一使用底部安全区操作栏，主行动固定可见；说明文案放在操作栏上方或可展开帮助中。
- 页面内容区预留与操作栏实时高度一致的安全底部间距，不能只写固定 `padding-bottom`。
- 主行动只保留一个；保存草稿、取消、导出等降级为次按钮或更多菜单。

## P1-4：数据新鲜度没有成为全局能力

- 全仓只有少数页面使用“更新于 / 更新时间 / 数据截至”等文案；财务工作台、客户经营、项目经营、业主首页等关键页面没有稳定的数据时间表达。
- “生命感”不能靠渐变和装饰，应靠真实业务脉搏：数据截至时间、刷新失败、同步状态、当前节点、责任人和下一步。
- 建议在经营型页面统一提供：
  - `数据截至 10:22`；
  - `本次刷新失败，显示上次成功数据`；
  - `来自项目/合同/资金流水` 的数据来源提示；
  - 无数据时区分“没有记录”和“尚未同步”。

## P1-5：视觉系统存在“Token 已建立，但局部仍在漂移”

### 现象

- `src/uni.scss` 已定义品牌、语义、文本、Surface、Elevation、Radius、Spacing、Typography、Motion 和 Z-index Token，这是正确基础。
- 但样式中仍有大量裸字号和裸圆角：
  - 约有 285 处 `font-size: 20rpx`、103 处 `22rpx`、36 处 `24rpx`、24 处 `18rpx`；
  - 约有 290 处 `$jzb-radius-sm`、184 处 `$jzb-radius-pill`，同时散布 `6/10/14/15/17/18/20/22/24/26/28/30/32/34/36/44rpx` 等一次性圆角；
  - 多处使用 `linear-gradient`、`radial-gradient`、白色透明度边框和局部重阴影。
- `npm run check:ui` 通过，证明裸色值和部分浮层规范受控；但它不检查字号、间距、圆角、对比度、触控热区和全页视觉一致性。

### 建议

- 将“视觉 Token 门禁”扩展到字体、间距、圆角、触控尺寸、图片 alt/aria、七态和对比度。
- 收敛为移动端 4–5 档圆角、3–4 档间距和 5–6 档字阶；禁止在页面新增一次性字阶和圆角。
- 头部渐变保留在首页/经营驾驶舱等品牌页；详情页、表单页和普通列表页优先使用 plain header，避免每个页面都像品牌 Hero。
- 建议把语义色拆成成对的 `*Text` 与 `*Surface`，从源头解决“颜色好看但文字对比不足”的冲突。

## P2-1：业主端应从“精美展示”继续走向“真实决策”

### 当前优点

- “我的家”作为项目身份入口，比通用员工首页更符合业主心智。
- 当前阶段、整体进度、待确认验收、家的记录和服务团队都能帮助业主建立信任。
- 业主子品牌 Token 与员工端区分明确，不需要强行统一成同一种青色工作台。

### 需要收口的地方

- “此刻，先看这一件事”“一份可追溯的装修档案”“每个岗位都对结果负责”等表达有编辑感，但如果同时出现较多，容易变成作品集文案，而不是业主当下要做的动作。
- 8 个记录入口等权排列时，业主仍需自己判断“现在最重要的是验收、付款还是变更”。
- 历史截图中的员工启动引导出现在业主首页，说明角色分支曾经混入过内部内容。当前源码已经拆分，但必须用当前真机截图重新确认。
- 业主首页的加载和失败提示位于页面底部，且空态先出现、加载/失败提示后出现，状态顺序需要修正。

### 建议

- 首屏只保留一个真实待办：例如“阶段验收待确认，截止 10-30”，直接进入验收证据。
- 把 8 类记录压缩为：前 3 个与当前阶段相关 + “查看全部档案”；其余降低权重。
- 首页增加“最近同步”或“数据截至”，让业主知道记录是否及时。
- 保留暖色子品牌，但去除纯装饰光斑和抽象价值陈述；每一屏的功能文案都必须能推动查看、确认、反馈或付款。

## P2-2：不建议给小程序加入装饰性 2.5D / 3D

当前小程序的核心价值是移动执行、证据留存和下一步动作，不是空间展厅。没有真实业务数据的 2.5D/3D 会：

- 增加加载和渲染成本；
- 占用首屏和弱网下的关键空间；
- 让用户误以为可交互，却没有实际业务动作；
- 强化“AI 味”和作品集感，削弱工具感。

只有在以下条件满足时才考虑空间化：

1. 绑定真实项目、空间、施工阶段或材料位置；
2. 点击后能改变检查器、任务、验收或下一步；
3. 有 2D 列表/平面图等价替代；
4. 可退化、可关闭、可访问；
5. 在真机上证明比 2D 更快回答“在哪里、什么风险、下一步做什么”。

## 6. 页面级评价

| 页面 | 结论 | 主要优点 | 主要风险 | 建议 |
|---|---|---|---|---|
| 员工首页 | 可用但偏重 | 角色化、经营入口完整、数据资产丰富 | 多模块并列，首屏结论不稳定 | 按角色冻结首屏顺序；经营结论和待办优先 |
| BOSS 客户页 | 有洞察但拥挤 | 分组、指标、风险、下一步齐全 | 双栏 + 多筛选 + 多指标，小屏压力大 | 小屏默认聚焦客户区；指标折叠；卡片只留决策字段 |
| 项目列表 | 信息完整但扫描慢 | 风险、回款、阶段、成本都有业务意义 | 一张卡承载过多事实，单屏效率低 | 首层结论化，成本和人员移入展开区 |
| 财务工作台 | 结论清晰但状态危险 | 现金余额、风险待办、资金闭环、快捷入口有业务价值 | 首载/失败显示 0 或空态；区块过多 | P0 状态重构；首屏只保留现金、风险和下一步 |
| 报价工作台 | 产品真实性较强 | 客户/项目/金额/版本/停留天数/下一步完整 | 状态、金额、编号、时间和动作同屏较多 | 保留 3 行卡密度，动作层级再明确 |
| 报价详情 | 版本对比有价值 | 版本、草稿/待确认、金额、方案和推进动作可见 | 横向版本卡与底部动作可能拥挤 | 明确“当前版本”和唯一下一步；其余动作收纳 |
| 主材列表 | 链路清楚 | 待下单、建单/测量中、已进入采购分组明确 | 加载中仅文字；失败后伪装为空 | 统一七态；列表保留状态和下一动作 |
| 主材详情 | 业务上下文强 | 项目、厂家、测量/配送/安装、材料明细、单据导出齐全 | 失败后显示“不存在或无权访问”，错误语义混合 | 区分失败、无权限、不存在；主次操作降噪 |
| 合同增减项 | 专业度高 | 合同基线、变更前后金额、试算、审批和明细有业务抓手 | 长表单和来源选择器密度高；底部可能覆盖内容 | 分区/锚点、固定操作栏与安全区联动 |
| 财务登记 | 表单清楚 | 字段语义明确、帮助和风险提示到位 | 主提交按钮在首屏外；字段较多 | 固定底部提交；分组渐进披露 |
| 业主首页 | 有温度、有信任基础 | 我的家、阶段、验收、档案、团队叙事完整 | 抽象文案、等权卡片、加载/空态混用 | 一屏一个真实待办；增加数据新鲜度；修正状态 |

## 7. 建议的实施顺序

### 批次 A：先修“数据可信”，这是 UI 也是业务

1. 财务工作台、主材列表/详情、业主首页统一七态。
2. 禁止未知金额显示 0；禁止失败伪装为空。
3. 增加数据截至时间和刷新失败提示。
4. 更新当前版本真机截图，覆盖三档屏幕和核心七态。

### 批次 B：再修“移动执行效率”

1. 项目卡、客户卡、财务工作台建立首层/展开层。
2. BOSS 客户页小屏默认聚焦工作区。
3. 长表单统一底部安全操作栏。
4. 高频列表统一搜索、筛选、刷新、选中和返回恢复规则。

### 批次 C：最后修“视觉系统与 AA”

1. 修正 `text-3`、`primary`、`success`、`warning`、`owner-muted-2` 的对比度。
2. 收敛裸字号、裸圆角和一次性渐变。
3. 补充图片 `aria-label`、按钮语义、热区和状态文字。
4. 对所有关键页做真实设备视觉复核，不用 OCR/模型输出替代验收。
