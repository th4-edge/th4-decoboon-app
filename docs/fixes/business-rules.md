## 1. 客户（Customer）

### 1.1 客户阶段（stage）流转

固定八阶段：`intention 待首联 → following 跟进中 → pendingMeasure 待量房 → quote 方案报价 → sign 已签约 → construction 施工中 → done 已完工`，外加 `lost 已流失`。



* 阶段流转由后端状态机负责，前端只提交动作后重新拉取，不在本地维护状态机；

* 前端展示的 "销售阶段" 是从客户字段推导出来的视图（详见客户详情 SalesSteps），不是独立存储。

### 1.2 客户档案地址 vs 房屋地址



* `customer.addr` 是**线索级地址**（首次留资时填写，可能只到小区 / 片区）；

* `property.address` 是**房屋级档案**（量房、设计、报价、签约的实际对象）；

* **业务规则**：任何需要 "量房 / 报价 / 开工" 的动作，必须以 `property` 为准，不能用 `customer.addr` 判断。【FIX-003】

### 1.3 客户详情主按钮（primaryAction）判定顺序

从高到低，命中即停：



1. 有项目（`project.value` 非空）→ "查看工地"；

2. 有已确认 / 进行中报价 → "查看报价"；

3. 销售阶段 = quote 且有报价权限 → "生成报价"；

4. 销售阶段 = design 且有报价权限 → "进入设计转化"；

5. 销售阶段 = measure：

* 未约定量房时间 + 可约定 → "约定量房"；

* 已约定量房时间 + 未指定设计师 + 可指派 → "指定设计师"；

* 可录入量房 → "录入量房"；

1. 销售阶段 = follow + 可跟进：

* 可约定量房 → "约定量房"；

* 否则 → "写跟进"；

1. 销售阶段 = visit + 可跟进：

* 可约定量房 → "约定量房"；

* 否则 → "完善客户资料"。

**业务规则**：主按钮每屏唯一，且实心绿色主按钮只能有一个；高频次要操作（写跟进）用右下角 FAB 承载。【FIX-002】



***

### 1.3.1 手机号关键身份规则

- 客户手机号是营销身份、跟进和后续账号关联的关键字段。
- 客户完成首次有效跟进后，前端编辑入口必须锁定手机号，后端 `customer/customer/update` 必须拒绝修改手机号。
- 修改手机号不能只隐藏输入框或依赖前端校验。

### 1.4 业务员角色边界

- 业务员负责获客、首次跟进、客户建档、房屋档案、约定量房和客户营销交接。
- 约定量房后，营销主责从业务员转移到设计师；具体指定设计师由店长、团队负责人或企业负责人执行。
- 业务员可以只读查看本人客户的后续报价、合同、项目和业务流转状态。
- 业务员不得创建、编辑、提交、接受、驳回或转换报价，不得进入设计编辑、谈单和方案维护工作台。
- 客户详情在业务员视角下，量房后已存在报价时显示“查看报价流转”；尚未形成报价时显示“查看业务流转”，不得再出现“生成报价”或“进入设计转化”主按钮。
- 报价 Provider、报价详情和报价明细对业务员提供本人客户只读访问；报价 `save/update` 必须拒绝业务员写入。

## 2. 房屋（Property）

### 2.1 房屋与客户的关系



* 一个客户可以有多套房屋（`1:N`）；

* 客户详情页房屋区用横向 `scroll-view` 展示，不纵向堆叠；

* 同一时刻只有一套房屋是 "当前选中"（activeProperty），所有量房 / 设计 / 报价动作都挂在选中房屋上。

### 2.2 房屋状态（property.status）

`pendingMeasure 待量房 → measuring 量房中 → measured 已量房 → designing 设计中 → quoted 已报价 → contracted 已签约 → serving 施工中 → completed 已完工`。

### 2.3 房屋档案编辑



* 房屋卡片右下角有 "编辑" 入口，可改：小区、楼栋、房号、详细地址、面积、户型、备注；

* 后端接口：`property/property/update`，前端入口 `property-edit?customerId=xx&propertyId=xx`；

* **业务规则**：客户档案的 "意向小区 / 面积" 和房屋档案是两份数据，编辑房屋不会回写客户档案，反之亦然。【FIX-003】

### 2.4 量房记录判定



* `property.latestMeasureAt` 非空 = 该房屋已量房；

* **业务规则**：已量房的房屋不再显示 "约定量房" 和 "调整量房时间" 入口，避免重复量房。【FIX-003】

## 3. 量房（Measure）

### 3.1 约定量房的前置条件（canScheduleMeasure）

必须同时满足：



1. 当前角色有 `act:scheduleMeasure` 权限；

2. 客户阶段在 `intention / following / pendingMeasure`；

3. **客户至少有一套房屋档案**（`properties.length > 0`）；

4. **当前选中房屋尚未量房**（`!activeProperty.latestMeasureAt`）；

5. 客户尚未指定设计师，或当前角色是店长 / 老板（可替他人改）。

**业务规则**：不再用 `customer.addr` 是否为空判断 —— 有客户地址不等于有房屋档案。【FIX-003】

### 3.2 量房时间调整



* 已约定量房时间（`customer.measureAt` 非空）且房屋未量房时，房屋卡片显示 "已约定 MM-DD HH:mm 调整"；

* 点 "调整" 进入量房页，日期时间自动回填，保存即更新（`customer/customer/measure` 接口是 upsert 语义）；

* 量房时间必须晚于当前时间。

### 3.3 指定设计师



* 已约定量房时间但未指定设计师时，主按钮变为 "指定设计师"；

* 由店长 / 老板操作，从在职设计师列表中选择。

## 4. 跟进（Follow）

### 4.1 跟进记录入口



* 右下角 FAB（`JzFloatAdd`）"写跟进"，与客户列表页 "登记客户"FAB 同组件同视觉；

* 显示条件：有 `act:followCustomer` 权限 + 当前主按钮不是 "写跟进" 本身；

* 除 "跟进中" 阶段外，已转项目、已报价阶段也可通过 FAB 补记沟通。【FIX-002】

### 4.2 跟进方式

电话 / 到店 / 拜访 / 微信 / 视频 / 其他，五选一。

### 4.3 到店记录



* 由有 `act:recordVisit` 权限的角色（店长 / 老板 / 市场）触发；

* 每次记录会 `visitCount + 1`，需二次确认。

## 5. 项目（Project）与数据隔离（P0 红线）

### 5.1 项目列表按角色过滤（后端）

`project/project/page` 接口对不同角色返回不同范围：



* Boss / Finance：全公司项目；

* StoreManager：本门店项目；

* TeamLeader：本团队项目；

* Designer：自己设计的项目；

* PM：自己管理的项目；

* Marketer：自己带来的项目。

### 5.2 客户详情取项目的铁律



* **必须**传 `customerId`：`projectApi.list({ customerId })`；

* **禁止**在客户详情页用全量项目列表前端 `find` 后再 `[0]` 兜底；

* computed 匹配项目时必须双条件：`project.customer.id === 当前客户 id` && `project.property.id === 当前选中房屋 id`。

**业务规则**：这是 P0 级红线，历史上出过 "王武详情跳到李明工地" 的串号事故。【FIX-001】

### 5.3 通用反模式（所有详情页禁用）



```
// ❌ 禁止

const x = allList.find(item => item.y === activeId) || allList\[0]

// ✅ 正确：要么按维度拉取，要么严格匹配，匹配不到就是 null

const x = filteredList.find(item => item.y === activeId && item.customerId === currentId) ?? null
```

## 6. 按钮与 CTA 规则

### 6.1 单页主 CTA 唯一



* 一屏可见的主色实心按钮只能有 1 个；

* 高频次要操作：


  * 全局高频（写跟进）→ 右下角 FAB；

  * 阶段内次要操作（编辑房屋、调整时间）→ 卡片内小按钮 / 胶囊；

  * 破坏性操作（删除、取消）→ 二次确认弹窗。

### 6.2 浮窗 FAB 使用规范



* 组件：`JzFloatAdd`；

* 默认图标 `plus`（新增 / 登记），其他语义传 `icon` prop（如 `message` 用于写跟进）；

* 底部固定高度计算：`tabbar-height + 36rpx + safe-bottom`；非 tab 页 FAB 位置会偏高，通过页面 padding-bottom 补偿。【FIX-002】

## 8. 引导与进度状态规则

### 8.1 完成状态必须由真实领域数据派生

引导、待办、实施清单、资料完整度和节点进度中的“完成”，禁止使用写死的 `done: true/false`、演示数据或仅前端本地布尔值。必须明确数据来源、完成谓词、计数口径和异常态。【FIX-004 / ECD-008】

### 8.2 返回页面必须刷新可变状态

会因用户新增、编辑、删除而变化的状态，必须在页面重新显示时重新取数，或在跨页写入后使缓存失效。不能只在组件首次挂载时加载一次。【FIX-004】

### 8.3 必做与可选必须一致

必做/可选必须同时体现在文案、进度分母、下一步和验收用例中。可选步骤完成后不改变必做分母；必做步骤未完成时下一步必须指向正确对象。

### 8.4 首次入驻供应商完成口径

产品状态契约已冻结为“至少一个有效材料供应商且至少填写一个关联品牌”。供应商步骤为可选，不计入首次入驻 3 个必做分母，也不阻塞后续必做步骤；该冻结不构成独立验收通过。【FIX-004 / REQ-20260918-ONBOARDING-DEFECT-001】

## 9. 微信分包依赖规则

- 主包组件、页面和领域 API 严禁直接引用 `@/subpackages/**` 下的私有实现；跨分包复用的领域代码必须上移到 `src/domains/**`。【FIX-005】
- 分包页面可以引用主包公共组件和主包领域 API；主包不得反向依赖分包。
- 修改主包组件的领域依赖后，必须同时重新生成 `dist/dev/mp-weixin` 和 `dist/build/mp-weixin`，并检查编译产物中的 `require()` 路径。
