> 本目录是 "装得清小程序端"BUG 修复、需求变更、业务规则沉淀的唯一真源。
> 每次接到 BUG / 缺陷 / 需求变更，必须按本文件规定的流程执行，并把结论落盘到本目录下对应文件。

## 一、角色分工（一次修复 = 四个视角串行）



| 视角          | 职责                                          | 输出位置                                  |
| ----------- | ------------------------------------------- | ------------------------------------- |
| **诊断工程师**   | 复现、定位代码、给根因                                 | `log.md` 当条记录 "根因" 段                  |
| **修复工程师**   | 改代码、加注释、跑 type-check                        | src 代码 + 当条记录 "代码改动" 段                |
| **资深业务观察者** | 判断修复思路是否符合家装行业惯例、是否影响销售 / 履约闭环、是否会引发新的越权或串号 | 当条记录 "业务审查" 段 + `business-rules.md`   |
| **流程沉淀官**   | 把本次修复涉及的业务规则、用户操作口径写入知识库，供后期培训装企用户          | `business-rules.md` + `user-guide.md` |

四个视角必须全部走完，不允许只改代码不沉淀。



***

## 二、标准修复流程（每次必走）

### Step 1・复现与定界



* 在代码里定位到具体文件、行号、接口调用；

* 区分 "前端 bug / 后端 bug / 数据问题 / 产品规则缺失"；

* 若需要后端配合，先在 "根因" 段标注后端文件路径，不要静默改前端绕过去。

### Step 2・根因分析

按以下结构写，禁止用 "显示不对" 这类无法验收的描述：



1. 现象（用户看到什么、预期是什么）；

2. 触发条件（角色 / 客户阶段 / 数据状态）；

3. 因果链（从取数 → 计算 → 渲染 → 跳转，逐环定位）；

4. 影响面（grep 同类调用，列出受影响页面）。

### Step 3・修复方案



* 说明设计决策、引用的 Design Token、涉及的领域 API；

* 优先改 "取数口径" 和 "业务规则"，不要靠 `[0]`、兜底、`any` 这类手段掩盖问题；

* 代码里**必须加注释**说明：


  * 这段逻辑为什么这么写；

  * 历史上踩过什么坑（哪个 BUG 号）；

  * 后续维护者容易改错的点。

### Step 4・业务观察者审查（强制）

每条修复必须回答：



1. **行业对标**：家装行业（土巴兔、齐家、好好住、美团装修）同类场景是怎么做的？本修复是否符合？

2. **闭环检查**：从 "获客 → 跟进 → 量房 → 设计 → 报价 → 签约 → 施工 → 验收" 全链路看，本次改动会不会让某一步走不下去、或者让两个角色看到不一致的数据？

3. **权限与数据隔离**：BOSS / 店长 / 设计师 / 项目经理 / 客户多角色视角下，会不会出现越权看到别人客户 / 工地的问题？

4. **降级与空态**：数据缺失、接口失败、无房屋 / 无报价 / 无项目时，页面是否仍有合理表现？

任一项不通过，回到 Step 3 重做，不允许带着已知风险提交。

### Step 5・沉淀



* 在 `log.md` 追加一条记录（模板见下）；

* 在 `business-rules.md` 更新对应模块的业务规则；

* 在 `user-guide.md` 更新装企一线员工的操作口径（如果本次修复改变了操作方式）。

### Step 6・验证



* 跑 `npm run type-check`；

* 列出用户自测清单（角色 × 场景 × 预期）；

* 有后端改动时，明确标注哪个接口、哪段 SQL、是否需要刷数据。

## 三、记录模板（`log.md` 每条记录必含）



```
\## FIX-XXX · 标题

\- 日期：YYYY-MM-DD

\- 报告角色：BOSS / 店长 / 设计师 / PM / 客户 / 开发自测

\- 影响模块：客户 / 房屋 / 量房 / 设计 / 报价 / 项目 / 财务

\- 严重度：P0 数据串号/越权 | P1 主流程走不通 | P2 体验问题 | P3 文案/样式

\### 现象

（用户原话 + 预期行为）

\### 根因

（代码级因果链，含文件路径与行号）

\### 修复方案

（改了哪些文件、关键设计决策）

\### 代码改动

（文件清单 + 关键 diff 概述；具体注释见代码本身）

\### 业务观察者审查

\- 行业对标：

\- 闭环检查：

\- 权限与数据隔离：

\- 降级与空态：

\- 结论：通过 / 有保留（说明保留项）

\### 验证

\- type-check：通过 / 失败原因

\- 用户自测清单：

&#x20; 1\. 角色 × 场景 → 预期
```

## 四、文件职责



| 文件                  | 用途                          | 维护节奏      |
| ------------------- | --------------------------- | --------- |
| `README.md`（本文件）    | 工作 SOP，不轻易改                 | SOP 调整时改  |
| `log.md`            | BUG 修复台账，按时间倒序，新记录插最上面      | 每次修复必追加   |
| `business-rules.md` | 按模块沉淀业务规则（阶段流转、按钮显示条件、权限边界） | 每次修复后增量更新 |
| `user-guide.md`     | 面向装企一线员工的操作手册，按角色 / 场景组织    | 操作口径变化时更新 |



***

## 五、与既有文档的关系



* 业务设计的 "应然" 写在 `docs/01-业务设计说明书.md`、`05~08-各视角业务闭环.md`；

* 本目录沉淀的是 "实然"—— 线上实际跑出来、修出来的规则和坑；

* 当两者冲突时，先以本目录 `business-rules.md` 为准排查，再回头改业务设计文档。
