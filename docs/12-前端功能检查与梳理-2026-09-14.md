## 2. P0：上线/联调阻塞

### P0-1 核心 Provider 断链

按后端当前源码的 `@Service` 注册结果扫描，以下前端路由没有后端实现：

| 前端调用 | 调用位置 | 当前影响 |
|---|---|---|
| `bim/zone/list` | `domains/base/api.ts`，由 `pages/task/edit.vue`、`pages/project/plan-edit.vue` 调用 | 任务编辑、施工计划排期初始化失败 |
| `bim/construction/page` | `domains/base/api.ts`，由 `pages/project/plan-edit.vue` 调用 | 施工工艺/施工项目录无法加载 |
| `bim/material/page` | `domains/base/api.ts` | 预埋的材料选择能力不可用 |
| `bim/gift-pack/page` | `domains/base/api.ts` | 预埋的礼包能力不可用 |
| `identity/customer/accept` | `domains/identity/api.ts` | 业主邀请接受链路未闭环 |
| `project/material-plan/save` | `domains/material/api.ts` | 后端只有 `project/material-plan/update`，保存契约不一致 |
| `statistic/workbench/report` | `domains/statistic/api.ts` | 对应统计能力不可用 |
| `statistic/dashboard/report` | `domains/statistic/api.ts` | 对应统计能力不可用 |
| `statistic/project-health/report` | `domains/statistic/api.ts` | 对应项目健康度能力不可用 |

当前必须立即处理的两条：

```text
任务编辑:
pages/task/edit.vue
  -> baseApi.zones()
  -> bim/zone/list
  -> 后端无 Provider

施工计划排期:
pages/project/plan-edit.vue
  -> Promise.all([
       baseApi.zones(),
       baseApi.craftCatalog()
     ])
  -> bim/zone/list
  -> bim/construction/page
  -> 后端均无 Provider
```

验收要求：

- `task/edit` 能正常打开并选择区域、阶段、负责人。
- `project/plan-edit` 能正常加载区域和施工项，不出现初始化 Promise 失败。
- 前端路由与后端 `@Service` 必须一一对齐，不能依赖网关隐式别名长期兜底。
- 不使用的预埋 API 要么实现，要么删除，避免形成“看起来可用、实际必然失败”的死接口。

### P0-2 客户详情信息架构仍未按 `AGENTS.md` 落地

`src/pages/customer/detail.vue` 仍然保留以下重复：

| 问题 | 当前证据 | 影响 |
|---|---|---|
| 同一条销售链路拆为 3 个区块 | `业务流程`、`设计转化`、`方案报价` | 用户不知道三个区块的先后关系 |
| 同一动作有多个名字 | “设计转化”“开始设计转化” | 用户无法判断是不是同一个动作 |
| 房屋信息重复 | 房屋横向卡 + “当前房屋”操作条 | 同一房屋表达两次，增加认知和滚动成本 |
| 到店次数重复 | 客户身份标签 + 可点击信号胶囊 | 数据展示与记录动作边界不清 |
| 写跟进重复 | 跟进区块标题入口 + 底部操作条 | 同一入口出现两次 |
| 电话/复制难识别 | 两个纯图标按钮 | 用户需要猜测图标含义 |
| 主色操作过多 | 房屋边框、状态标签、多个主按钮 | 页面没有唯一主 CTA |
| key-value 不一致 | 标签列宽 `150rpx`，多值未统一 | 与规范要求的两列栅格不一致 |
| 空值文案不统一 | `-`、`无`、`尚未录入` 混用 | 用户无法形成稳定阅读预期 |

必须按 `AGENTS.md` 第 15 节执行：

- 新建 `SalesSteps`，固定 `到店 → 跟进 → 量房 → 设计 → 报价` 五步。
- 删除独立“当前房屋”区块，合并到 `HouseCard`。
- 客户卡只保留身份和联系动作，到店次数下沉。
- 页面只保留当前阶段一个主 CTA。
- 跟进入口只保留一个主要入口和一个明确次要入口，不能重复出现同权入口。
- 长编号折叠，空值统一为 `—`。
- 页面主色高亮/实心操作最多 2 处，其中实心主按钮只能 1 个。

### P0-3 错误态会被成功数据遮住

`customer/detail.vue` 的渲染顺序是：

```text
!c && !booted  -> loading
c              -> 正常页面
loadError      -> 错误页
else           -> 客户不存在
```

`load()` 先成功设置 `c`，随后任一依赖请求失败时会写入 `loadError`，但模板仍优先渲染 `c` 分支，因此用户看到的是“部分数据页面”，错误页不会出现。

同一问题在多个详情/列表页以不同形式存在：

- 页面初始化 `load()` / `refresh()` 没有局部 `catch`。
- 全局 `errorHandler` 只能弹 toast，不能提供页面级重试。
- `project/detail.vue`、`quote/detail.vue` 存在 `catch(() => [])` 静默降级，用户会把“加载失败”误认为“暂无数据”。
- 扫描发现 36 个异步加载/动作函数没有局部异常处理。

验收要求：

- 每个异步页面明确区分 `loading / empty / error / success`。
- 核心请求失败时不能让页面进入假成功状态。
- 错误态必须显示错误说明和“重新加载”。
- 可选数据静默降级必须加注释说明，且不能吞掉核心请求错误。

### P0-4 列表静默截断

实际列表请求大量使用固定页大小：

```text
customer/customer/page        size=200
project/project/page          size=200
site report/page              size=200
finance receipt/page          size=200
finance payment/page          size=200
finance ledger/page           size=300
```

未发现 `onReachBottom`、加载更多状态、`hasMore` 或游标分页实现。超过固定数量的数据会“看起来已加载完”，但实际缺失，属于数据正确性问题。

验收要求：

- 客户、项目、报价、任务、动态、财务流水优先改为分页。
- 页面底部具备加载中、加载失败、没有更多三种反馈。
- 下拉刷新重置到第一页，不能覆盖旧的加载更多请求。
- 列表总数、筛选结果和分页数量口径一致。

### P0-5 微信端关键入口未闭环

这是 `docs/10-上线前梳理与优化清单.md` 已记录且本次代码核对仍成立的问题：

- `pages/auth/login.vue` 微信登录仍是提示“接入中”。
- 业主注册入口仍为“即将开放”。
- 业主邀请接受入口仍为“待开放”。
- 用户协议、隐私政策只是文本，不是可打开的落地页。
- 未配置正式 appid，未接入订阅消息。

影响：

- 业主角色无法通过完整自助路径进入并使用“我的家”。
- 微信小程序提审合规和正式发布会被阻断。
- 节点、验收、逾期等关键事件只能站内看到，无法主动触达。

## 3. P1：功能一致性与可维护性

### P1-1 页面级权限规则覆盖不完整

当前 30 条 `ROUTE_RULES` 未覆盖以下角色敏感页面：

```text
customer/measure
customer/measure-record
project/detail
project/plan
project/members
project/album
stage/detail
task/detail
report/daily
accept/edit
msg/list
performance
manager/workbench
```

前端权限不是服务端权限的替代品，但这些页面存在角色差异较大的数据和操作。缺少页面级规则会导致：

- 非目标角色手输 URL 或代码误跳后进入空页面。
- 页面内部再次散落角色判断。
- 同一个能力在按钮、页面和 API 三处判断不一致。

建议统一按“查看 / 编辑 / 动作”补齐规则，并让 Tab、快捷入口、页面守卫共用同一份能力声明。

### P1-2 角色导航定义存在文档与代码不一致

代码 `ROLE_TABS` 中 `pm` 为：

```text
工作台 / 客户 / 项目 / 我的
```

README 的当前角色表中 `pm` 为：

```text
工作台 / 项目 / 动态 / 我的
```

同类问题还出现在角色能力描述和页面实际入口。需要确定唯一产品定义，再同步：

- `ROLE_META`
- `ROLE_TABS`
- `ROLE_ACTIONS`
- `roles/permission.ts`
- README 和角色闭环文档

### P1-3 角色判断散落在页面

`customer/detail.vue`、`customer/list.vue`、`index/index.vue`、`performance/index.vue`、`quote/detail.vue`、`project/detail.vue` 等仍存在较多 `session.role === 'xxx'` 分支。

建议：

- 能力判断统一走 `can(role, capability)`。
- 角色布局差异统一走 `ROLE_TABS` / `ROLE_ACTIONS`。
- 页面只消费能力布尔值，不直接读角色字符串。

### P1-4 三态覆盖不足

- 仅 2 个页面有显式 `loadError`。
- 仅 14 个页面使用 `JzSkeleton`。
- 32 个页面使用 `JzEmpty`，但空态与错误态语义未统一。
- 多个详情页失败后仍显示旧数据，没有 stale 标识。

建议建立统一页面数据状态组件或 composable：

```ts
type PageState = 'loading' | 'success' | 'empty' | 'error'
```

### P1-5 关键按钮缺少一致的防重复和禁用反馈

已有一部分页面正确使用 `submitting`，但客户详情的微信、到店、指派设计师，以及其他详情动作仍存在：

- 未满足权限时元素仍可点击。
- 点击后因为 handler 内 `if` 静默返回，没有提示。
- 加载中按钮未统一 `loading` / `disabled`。
- 图标操作没有文字标签或可访问名称。

这不是服务端权限漏洞，但会造成“点了没反应”的体验问题。

### P1-6 组件拆分不达规范

- `design/scheme.vue` 644 行，超过页面 500 行限制。
- `index/index.vue` 525 行，超过限制。
- `customer/detail.vue` 499 行，处于上限但没有拆出 `SalesSteps`、`HouseCard`、销售阶段模型。
- 当前 `components` 多为平铺 `JzXxx.vue`，新组件应按 `components/XxxYyy/XxxYyy.vue` 组织。

## 5. 页面与功能梳理

### 5.1 客户转化域

| 页面 | 主要职责 | 当前问题 |
|---|---|---|
| `customer/list` | 客户筛选、搜索、负责人视图、待量房/待指派提示 | 全量 200 条，无触底分页 |
| `customer/detail` | 客户身份、房屋、销售阶段、跟进、设计报价、项目入口 | P0 信息架构重复，错误态被遮蔽，多请求串行 |
| `customer/edit` | 新建/编辑客户基础资料 | 加载无错误态；权限由路由统一保护 |
| `customer/follow` | 写跟进、下次跟进时间 | 表单页面，无列表分页需求 |
| `customer/measure` | 约定量房时间和房屋 | 权限规则缺失 |
| `customer/measure-record` | 录入量房事实和设计结论 | 权限规则缺失，未做统一异常页 |

目标闭环：

```text
登记客户
  -> 跟进
  -> 补充房屋
  -> 约定量房
  -> 指定设计师
  -> 量房记录
  -> 设计诉求/方案
  -> 报价
  -> 客户确认
  -> 转施工项目
```

客户详情必须成为这条链路唯一的阶段控制台。

### 5.2 设计转化域

| 页面 | 主要职责 | 当前问题 |
|---|---|---|
| `design/requirements` | 设计诉求池和进度 | 固定数量拉取 |
| `design/requirement` | 单个客户诉求录入 | 入口和阶段文案不统一 |
| `design/list` | 设计方案、报价、谈单入口 | 页面状态依赖多个请求 |
| `design/scheme` | 空间、设计项、施工项编辑 | 644 行，超过限制 |
| `design/talk` | 谈单 PPT 展示 | 预览和下游数据加载错误态不足 |

建议由一个明确的“设计转化”工作区承载，客户详情只显示当前设计阶段和唯一下一步。

### 5.3 报价与签约域

| 页面 | 主要职责 | 当前问题 |

| `quote/detail` | 报价明细、确认、合同/项目转换 | 下游请求静默失败，详情展示可能误判为空 |

核心验收：

```text
设计完成 -> 生成报价 -> 客户确认 -> 生成合同 -> 转施工项目
```

## 9. 最终结论

`th4-decoboon-app` 的领域结构和基础工程质量是可用的，但当前不能按“页面已开发完成”判断。

优先修复顺序必须是：

```text
Provider 断链
  -> 客户详情信息架构
  -> 列表分页与错误态
  -> 微信认证与合规
  -> 权限矩阵收敛
  -> Token 和组件工程化
```

在这六项完成前，不建议继续新增同等级业务页面，否则会扩大重复入口、重复数据和接口不一致。
