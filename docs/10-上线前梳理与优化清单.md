# 装得清小程序端（th4-decoboon-app）上线前梳理与优化清单

> 审查对象：`th4-decoboon-app`（uni-app + Vue3 + TS + Vite 微信小程序端）
> 审查方式：全量阅读 `src`（domains 39 文件 / pages 50 文件 / roles、core、components、composables）+ 架构文档 docs/01–09 + 运行 `vue-tsc --noEmit` + 缺陷模式检索（魔法字符串、硬编码颜色、N+1、分页、状态机等）
> 审查时间：2026-09-14
> 结论：**架构底子好，但尚未达到可提审上线状态**。有 6 项上线阻断（P0）、10 项高优先（P1），另有与「报价重构定案」的适配工作必须在发版前排期。

---

## 一、总体评价（先说做得对的）

1. **领域分层干净且落地扎实**：`domains/<domain>/{model,api,meta}.ts` 结构统一，页面只依赖领域 API，无页面内 `uni.request`、无本地 mock、无 DTO 包装层，符合五条铁律。
2. **权限体系是亮点**：`Capability` 矩阵（`roles/permission.ts`）+ 页面路由拦截器（`roles/guard.ts`，统一拦截 navigateTo/redirectTo/reLaunch/switchTab）+ 明确"服务端仍须强制校验"的边界，比多数同类项目完整。
3. **设计系统成型**：`uni.scss` Token 完整（品牌/语义/文字/表面/阴影/圆角/间距/字号），`base.scss` 提供卡片、按钮、表单、空态等语义类；`JzIcon` 线性图标统一使用 306 处，无 emoji/字符图标。
4. **工程健康度不错**：`vue-tsc --noEmit` 全绿（0 错误）；无 TODO/FIXME；路由集中 `P.*` 管理；HTTP 层统一处理 401 与错误文案；`.gitignore` 正确忽略 dist/node_modules。
5. **文档体系完整**：docs/01–09 覆盖业务、交互、视觉、架构、各角色闭环，为后续迭代留了基线。

**问题集中在上线适配层**：平台能力（微信登录/订阅消息/分包）、数据层（分页/N+1）、与已定案报价重构的对齐，以及一些执行层面的走样（硬编码颜色、角色 if/else）。

## 三、高优先缺陷（P1，上线前至少完成主体）

### 3.1 数据层：分页缺失 + N+1 查询（上线后数据量增长即暴露）

| # | 问题 | 证据 |
|---|------|------|
| P1-1 | **所有列表硬编码 size 全量拉取，无分页/触底加载** | `size: 200/100/300` 硬编码 18 处（`project/api.ts:111`、`crm/api.ts:107`、`finance/api.ts:199` 台账 size:300、`identity/api.ts:166,185` 等）；`PageResult.total` 被 `listOf` 丢弃 |
| P1-2 | **首页/详情存在 N+1** | `pages/index/index.vue:209-214` 对每个项目串行 `acceptanceApi.listByProject`；`quote/edit.vue:78` 对每套方案逐套 `scheme()` 拉全量明细；`project/detail.vue` onShow 每次全量重载 5+ 接口 |

影响：客户/项目/流水量上来后首屏慢、流量放大、列表缺数据。建议：领域 API 统一返回 `{list,total}` 分页结构（catalogApi.page 已是好范式），列表页接 onReachBottom 分页；首页验收/明细类数据改为服务端聚合接口（statistic 已有先例）。

### 3.2 状态机前移，违反铁律三与 docs/04 §139 约定

| # | 问题 | 证据 |
|---|------|------|
| P1-3 | **前端直接改业务状态** | `project/api.ts:135-142` `openStage` 直接 post `status:'doing' + actualStart + owner`；`schedule/api.ts:112-117` `verifyTask` 直接 `status:'done'`；`trade/api.ts:193-198` `transition` 直接改报价状态 |

docs/04 §139 明确"业务动作优先保存对应实体，由后端监听器/服务推进状态"。当前页面提交状态快照，后续状态机一旦在后端收紧（如阶段前置条件、并发校验），前端这套调用必然失效。建议：openStage/verifyTask 改为领域动作接口（`stage/open`、`task/verify`），前端只提交业务对象+重拉。

### 3.3 报价模型与已定案重构未对齐（详见第五节）

| # | 问题 | 证据 |
|---|------|------|
| P1-4 | **前端 Quote 结构是旧的 regionGroups/constructionGroups/materialGroups/otherGroups + items 平面模型** | `domains/trade/model.ts:40-74`、`trade/api.ts:110-116`；`quote/edit.vue` 走 `quote/save` 传 mode/templateId/designId |

与定案内核（Quote→QuoteVersion→QuoteSection→QuoteLine、SellableItem 根+六类明细）不一致，需要一次模型+路由适配版本（见第五节）。

### 3.4 架构走样与工程债

| # | 问题 | 证据 |
|---|------|------|
| P1-5 | **枚举/单位映射重复 11+ 处** | `enumValue()` 在 identity/crm/project/finance/design/catalog/schedule/site/acceptance/collab/trade 共 11 个 api 文件重复；`UNIT_NAMES`/`UNIT_API` 在 catalog/design/trade 重复 3 份；UI↔API 枚举映射散落，改一个枚举要改多个文件且易漏 |

### 3.5 其他值得注意的执行问题

- **金额单位口径存疑**：`core/format.ts:15-19` 注释写"分→元展示（入参统一为元）"但实现按元处理；`quote/edit.vue:31` 折扣用字符串 `'100'` 前端换算。需与服务端明确单位口径（元/分）并统一，财务域出错是事故级。
- **API 路由与架构文档不一致**：代码实际用 `quote/page|info|save`、`project/project/page`，docs/04 §4.2 目标路由是 `trade/quote/*`、`project/site/*`——要么改代码要么改文档，二选一并固化。
- **静默降级 5 处** `catch(() => [])`，列表初始化失败页面无感知，需区分"可选数据"与"核心数据"。
- **`crmApi` 运行时读 `session.role` 决定路由**（`crm/api.ts:106`）——API 层依赖全局会话，角色切换/多企业场景易错，建议由页面显式传入或拆独立接口。

## 四、优化方向（P2，上线后迭代）

1. **性能体验**
   - 骨架屏覆盖：`JzSkeleton` 目前仅 5 页使用，列表/详情页统一补；空态已有 JzEmpty 但可统一 loading→empty→error 三态组件。
   - 详情页缓存：`project/detail.vue` 每次 onShow 全量重载，建议按项目维度做内存缓存 + 下拉刷新失效。
   - 图片链路：统一压缩（`uni.compressImage`）+ 上传队列 + 失败重传，汇报场景尤其需要。
2. **产品能力**
   - 裂变/获客：微信分享卡片、效果图海报、业主邀请码分享图。
   - 定位打卡：manifest 已声明 `getLocation`（工地打卡与位置汇报），落地打卡页面/巡检定位留痕。
   - 消息中心升级：站内消息已具备，补齐角标推送（订阅消息）、已读/未读分组、关键动作直达。
3. **工程质量**
   - 补 eslint/prettier/husky + CI（type-check + build + 小程序上传）；目前 scripts 只有 dev/build/type-check。
   - 组件测试/关键流程 E2E（登录→建客户→量房→报价→立项→任务→验收闭环）。
   - 将 `待修复问题.md` 单行清单迁移到 issue/文档化缺陷台账。
