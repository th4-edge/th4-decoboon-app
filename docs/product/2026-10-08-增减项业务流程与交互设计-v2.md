## 0. 结论摘要

装得清对增减项的最终定义：

> **增减项不是"改报价分项"，而是客户找设计师线下确认后，由设计师形成的正式合同变更单。原报价与原合同行不变，客户可通过小程序同频看到；企业内部审批通过后，合同金额、应收、施工任务、材料计划与项目成本在同一事务内联动。**

一句话链路：

```text
客户提出变更诉求（找设计师）
  → 设计师与客户线下确认（改什么、多少、工期影响）
  → 设计师形成增减项变更单（登记客户线下确认证据）
  → 企业内部审批（BOSS / 财务）
  → 生效：合同额 / 应收 / 任务 / 材料 / 成本同事务联动
  → 客户在小程序同频查看该变更单
  → 项目经理 / 材料 / 财务执行履约
```

三条不可违反的主规则：

1. **触发源是客户，主责是设计师。** 客户是变更诉求来源；设计师是客户对接、线下确认与变更单形成的第一责任人。
2. **客户线下确认是变更单的创建前置事实。** 客户签认是"形成变更单之前/之时已发生"的事实，由设计师登记并保留证据；不是审批后的补确认。
3. **企业内部审批是生效门槛。** 客户线下确认不替代企业审批；只有"客户线下已确认 + BOSS/财务审批通过"才触发合同与履约重算。

## 1. 业务定义与边界

### 1.1 定义

增减项 = 合同生效、项目创建之后，针对合同范围的正式变更单（`ContractChange` + `ContractChangeItem`）。

五类变更保持不变：

| 类型 | 枚举 | 语义 | 金额符号 | 未开始/未采购 | 已开始/已采购 |
| --- | --- | --- | --- | --- | --- |
| 增项 | `Add` | 新增范围 | 正 | 新增任务 + 材料计划 | 同左，保留原事实 |
| 减项 | `Remove` | 取消范围 | 负 | 任务取消、材料计划冲减 | 保留原事实，生成差异 |
| 替换 | `Replace` | 甲换乙 | 净差额 | 关闭原范围，生成替代任务/材料 | 保留原事实，生成替代范围 |
| 数量变更 | `Quantity` | 数量调整 | 差额 | 直接调整未执行对象 | 保留原事实，生成差异对象 |
| 价格变更 | `Price` | 单价调整 | 差额 | 直接调整未执行金额 | 保留原事实，生成差异对象 |

强制口径：**原报价与原合同行永久不变**，只更新合同 `currentAmount`、项目合同额与派生的应收/任务/材料/成本。替换/数量/价格必须关联原合同行；增项/减项选填。

### 1.1.1 增减项内容 = 报价分项的增加 / 变更 / 删除组合

用户 2026-10-08 明确：**增减项的内容就是对报价分项进行增加、变更、删除的组合。**

五类变更与三种内容操作对应关系：

| 内容操作 | 对应变更类型 | 说明 |
| --- | --- | --- |
| 增加 | `Add` | 新增报价分项（原报价没有的范围） |
| 删除 | `Remove` | 取消原报价范围内的分项 |
| 变更 | `Replace` / `Quantity` / `Price` | 对原报价分项做替换、数量调整或单价调整 |

口径：

- “报价分项”在合同生效后冻结为原合同行（`ContractLine`）；增减项以 `ContractChangeItem` 承载增量，**不修改原报价 `QuoteLine` 与原合同行**。
- 替换/数量/价格必须关联原合同行；增项/减项选填来源行。
- 多条增加/变更/删除可以组合为**一张变更单**（批量），一次审批、一次生效、一次履约联动。

### 1.2 边界

- **报价阶段改清单不叫增减项**：签约前是报价修订/新版本；只有合同生效、项目创建后才走增减项。
- **客户不直接形成变更单**：客户只提出诉求与线下确认；变更单由设计师（或经授权的内部角色）在系统中形成。
- **客户小程序是"同频可见"，不是"自助确认"**：本期客户可查看所属变更单，不提供客户自助确认/驳回按钮。
- **已生效变更不可编辑/删除/撤回**：如需再改，新建下一张变更单（增量追溯）。
- **已发生采购/施工事实只可补偿**：减项不删除历史任务/材料，走差异任务、采购调整、退货冲减。
- **客户异议不留拒绝状态**：客户在小程序看到后如有异议，由设计师新建一张反向变更单，走同一审批链。

## 2. 真实业务场景（强制 ≥ 2）

### 场景一：客户微信找设计师加做背景墙

- **使用人**：客户李女士、项目设计师张工。
- **触发事件**：客户在工地或微信提出"客厅背景墙要增加灯带和木饰面收口"。
- **当前动作**：客户找设计师沟通；设计师确认范围、用量、报价与工期影响；客户线下确认。
- **系统下一步**：设计师在 App「发起增减项」选增项、关联原合同行、录入金额与签证照片，登记客户线下确认时间/方式/证据，提交后生成一张待审批变更单。
- **异常处理**：无客户线下确认证据不能提交；变更后合同额 < 0 时前端与服务端同时拒绝；接口失败显示"变更状态暂不可确认"并保留重试。

### 场景二：客户要更换已下单的主材

- **使用人**：客户王先生、设计师、财务。
- **触发事件**：客户想把手感不佳的已下单柜体板材换成另一款。
- **当前动作**：客户与设计师线下确认替换方案与新价格；设计师形成"替换"变更单，关联原合同主材行。
- **系统下一步**：审批通过生效后，系统保留原材料下单事实；未到货部分调整采购单并下调应付，已到货部分强制走退货单冲减应付与实际成本，再形成新的材料计划。
- **异常处理**：已付款部分转"待协商"；成本不完整时利润显示"成本未完整"，禁止 0 成本伪利润。

### 场景三：客户在小程序看到变更单后提出异议

- **使用人**：客户、设计师。
- **触发事件**：变更单生效后，客户在 App「我的家 · 增减项」看到金额或范围与线下理解不一致。
- **当前动作**：客户联系设计师表达异议。
- **系统下一步**：设计师核查后新建一张反向变更单（如原增项则等额减项）；系统不新增"客户拒绝"状态，不修改已生效变更单。
- **异常处理**：反向变更同样需要客户线下确认与企业审批；重复提交幂等。

### 场景四：一次设计改版涉及十几条材料

- **使用人**：设计师。
- **触发事件**：一次设计调整涉及十几条材料替换/调量。
- **当前动作**：客户线下确认整体调整后，设计师在 Web 或 App 批量录入多行。
- **系统下一步**：一次提交形成**一张变更单 + 多行明细**；金额服务端重算；审批通过后整单生效。
- **异常处理**：任一行金额非法整单拒绝，不静默丢行；批量与逐条金额口径一致。

## 3. 角色与责任

| 角色 | 责任 | 不可做 |
| --- | --- | --- |
| 客户 | 提出变更诉求；与设计师线下确认；小程序同频查看所属变更单 | 不直接形成变更单、不审批、本期不自助确认 |
| **设计师（主责）** | 承接客户诉求、线下确认、形成变更单、登记客户确认证据、作为记录人 | 不审批 |
| 项目经理 | 履约执行：落任务、落材料、补现场事实；可按授权协助代录 | 不是默认发起人，不审批 |
| BOSS / 财务 | 企业内部审批；决定受理与执行；成本可见 | 不改变客户已线下确认的事实 |
| 店长 / 团队负责人 | 按数据范围查看、跟进、代管 | 不审批（店长/团队长） |
| 业务员 | 按数据范围查看自己客户项目 | 不发起、不审批 |
| 平台 / 系统 | 数据范围收敛、幂等、留痕、履约联动 | 不得跨租户、不得伪造客户签认 |

角色边界（沿用现行）：
- 审批仅 `Boss / Finance`。
- 成本仅 `Boss / StoreManager / Finance` 可见；PM/设计师/业务员响应中不返回成本。
- 客户签认证据必须与内部操作人分开记录：客户签认事实 + 设计师（或授权记录人）登记事实。

## 4. 业务对象与需要新增的事实字段

现有对象：`ContractChange`（变更单）+ `ContractChangeItem`（明细），继承项目 `company → store → team → owner`。

为承载新口径，变更单需要明确以下**客户确认事实**（字段名与落库方式由研发设计，业务语义如下）：

| 事实 | 语义 | 必填 | 说明 |
| --- | --- | --- | --- |
| 客户线下确认时间 | 客户实际确认的时间 | 必填 | 不能只用系统提交时间代替 |
| 客户确认人 | 客户姓名/称谓 | 必填 | 客户本人或其授权代表 |
| 确认方式 | 当面 / 微信 / 电话+书面等 | 必填 | 用于回溯 |
| 客户确认证据 | 签名、照片、聊天/纸质记录 | 至少 1 项 | 缺证据不得形成单 |
| 内部记录人 | 形成变更单的设计师/授权角色 | 必填 | 系统登录人，自动记录 |
| 客户线下确认备注 | 客户特别说明 | 选填 | 不替代证据 |

`customerConfirmed` / `customerConfirmedAt` 的现有语义需要重新定义：新口径下它是**创建前置事实**，不再是"审批后的后置状态动作"。历史 `CustomerConfirmed` 状态作为历史生效状态兼容映射，具体枚举与迁移方案由研发设计评审确定。

## 5. 状态机与时序（业务口径）

### 5.1 三个独立事实

```text
事实 A：客户线下确认（由设计师在形成变更单时登记）
事实 B：企业内部审批（BOSS / 财务）
结果 C：生效（A 与 B 同时满足，审批通过即触发履约重算）
```

两个事实相互独立、缺一不可；**客户线下确认先发生，企业审批决定是否执行**。

### 5.2 对外状态（App 显示）

```text
形成变更单（客户线下已确认）
  → [待审批]
      ├─ BOSS/财务审批通过 → [已生效]（合同额/应收/任务/材料/成本同事务联动）
      ├─ BOSS/财务驳回     → [已驳回]
      └─ 发起人/同团队负责人撤回 → [已取消]

已生效后客户有异议 → 新建反向变更单（不新增客户拒绝状态）
```

对外状态只有四个：**待审批 / 已生效 / 已驳回 / 已取消**。客户线下确认作为事实条展示（客户、时间、方式、证据），不单独占用一个业务状态。

### 5.3 与 v1.2 的差异

| 维度 | v1.2（旧） | v2.0（本设计） |
| --- | --- | --- |
| 触发源 | 施工现场发现 | 客户找设计师 |
| 发起主责 | 项目经理现场发起为主 | 设计师形成变更单 |
| 客户签认时序 | 审批通过后现场代登记 | **形成变更单前已线下确认** |
| 状态节点 | `Pending → Approved → CustomerConfirmed` | `待审批 → 已生效 / 已驳回 / 已取消` |
| 客户端 | 不登录，不展示 | **小程序同频可见（只读）** |
| 生效时点 | 客户确认后 | **内部审批通过后**（客户线下确认已前置） |

## 6. 金额与成本口径（保持不变）

```text
变更后合同金额 = 合同 currentAmount + Σ(已生效变更单 amount)
变更后项目合同额 = 变更后合同金额（同步）
变更款应收 = amount（正数生成应收；负数冲减未收应收）
变更成本 = Σ(item.costDelta)
项目毛利 = 项目收入 - 项目成本
```

强制三条（`MET-002`）：
1. 任一应计成本缺失 → `costComplete=false` → 毛利/毛利率为空，显示"成本未完整"，禁止 0 成本伪利润。
2. 变更后合同金额 < 0 服务端拒绝。
3. 预计毛利/动态毛利/结算毛利三者不混用，页面写明口径。

减项应收处理：正数生成"变更款"应收（现在 +7 天）；负数按未收余额逐笔冲减；超过未收余额则拒绝，提示"请先调整应收计划"。

## 7. 客户同频可见（小程序）

### 7.1 可见范围（白名单）

| 可见 | 不可见 |
| --- | --- |
| 变更单号、类型、原因 | 成本、成本变化、毛利/毛利率 |
| 变更明细（名称/规格/数量/单价/金额变化） | 内部审批意见、内部备注 |
| 变更前 / 本次 / 变更后合同额 | 其他客户/项目数据 |
| 当前状态、生效时间 | 内部人员成本相关字段 |
| 客户线下确认时间/方式/证据 | 权限、角色、内部操作日志明细 |

### 7.2 入口与展示

- 客户小程序首页快捷入口「增减项」→ 业主端只读增减项页。
- 客户项目详情 → 「增减项」。
- 展示变更单列表与详情：编号、状态、本次金额、变更前后合同额、明细、客户线下确认证据。
- **本期不提供客户自助确认/驳回按钮**；有异议联系设计师，由设计师新建反向变更单。

### 7.3 同频口径

客户看到的金额、状态、合同当前额必须与内部变更单、合同档案同源同口径，禁止前端兜底或本地重算。

## 8. 权限与数据范围

- 变更单与派生对象继承项目 `company / store / team / owner`。
- 数据可见范围：BOSS 全企业；店长本店；团队负责人本团队；PM/设计师参与项目；业务员自己客户项目；客户仅自己项目。
- 跨企业/门店/团队/项目不可见，直接伪造 ID 返回无权限且不泄露对象存在性。
- 服务端强权限；前端隐藏按钮不构成权限。
- 客户只读接口必须单独裁剪：不得返回成本、内部意见、内部人员信息。

## 11. 验收标准（交 acceptance）

**正向**
1. 客户→设计师线下确认→设计师形成变更单（含客户确认证据）→ 待审批。
2. BOSS/财务审批通过 → 已生效 → 合同额/项目额/应收/任务/材料/成本同事务联动。
3. 所属客户在小程序看到该变更单，金额/状态/明细与内部一致。
4. 五类变更分别生成正确金额与履约联动。

**反向/越权**
5. 无客户线下确认证据不能形成变更单。
6. 非 BOSS/财务不能审批；非数据范围不可见；跨租户伪造 ID 返回无权限。
7. 客户只读响应不含成本、内部意见、其他项目数据。
8. 变更后合同额 < 0 被拒绝；减项超过未收应收被拒绝。
9. 已生效不可编辑/撤回；撤回仅待审批。
10. 客户异议不新增拒绝状态，由设计师新建反向变更单。

**幂等/边界**
11. 重复提交、重复审批、重复生效不产生重复应收/任务/材料。
12. 成本不完整时利润为空并显示"成本未完整"。

**跨端一致**
13. App 内部页、客户同频页、合同档案三处金额与状态一致。
14. 原报价与原合同行保持不变。
