# 2026-10-08 App 业务对象专用选择器改版设计

> 状态：Phase 1 已实现（FIX-033），T15/T16/T17 评审结论见第 10 节；待微信开发者工具真实点击验收  
> 关联事实源：`DEC-021`、`BR-019`、`DEC-023`、`BR-021`、`DEC-024`、`BR-022`、`DEC-025`、`BR-023`、`DEC-026`、`BR-024`、`DEC-028`、`BR-026`

## 1. 结论

当前 App 中新建报价、套餐确认、方案分项等流程仍大量使用原生 `<picker>` 或页面内扁平数组。它们只展示名称/价格，缺少负责人、状态、阶段、版本、面积、可报价条件、适用户型、成本权限等业务事实，不符合业务对象专用选择器规范。

正确方向不是做一个“所有业务对象通用选择器”，而是：

- 每个业务对象保留自己的业务模型、首屏数据、筛选维度和卡片摘要；
- 所有对象选择器统一入口、搜索分页、选择/清除、失败恢复、一次性回传和服务端复核机制；
- 项目选择器只作为机制参考，不作为客户、方案、套餐的 UI 直接复制模板。

## 3. P0 选择器设计

### 3.1 客户选择器

- 适用场景：新建报价、新建其他需要客户上下文的单据。
- 首屏默认：当前数据范围内客户，按最近跟进/风险/创建时间排序。
- 主筛选：负责人、客户状态、最近跟进状态。
- 搜索：姓名、手机号、小区、地址。
- 卡片字段：客户姓名、手机号、负责人、当前阶段、房屋数、最近跟进时间、下次跟进时间。
- 选择结果：客户对象引用；不得默认第一条。
- 选择后行为：加载该客户房屋、报价、项目状态；更换客户时清空房屋、方案、套餐和已编辑报价上下文。

### 3.2 房屋选择器

- 前置条件：必须已选客户。
- 首屏默认：该客户全部房屋，按小区/楼栋/房号和状态排序。
- 主筛选：房屋状态、量房/设计/报价进度。
- 搜索：小区、楼栋、房号、地址、面积。
- 卡片字段：小区/楼栋/房号、面积、户型、量房状态、设计状态、设计师。
- 选择结果：房屋对象引用；禁止用第一条兜底。
- 上下文失效：更换客户时立即清空房屋选择；原房屋不属于新客户时禁止保留。

### 3.3 设计方案选择器

- 前置条件：已选客户；可选按房屋过滤。
- 首屏默认：该客户全部方案，优先展示可报价方案。
- 主筛选：方案状态、是否可报价、房屋。
- 卡片字段：方案名称、版本、状态、房屋、面积、区域数、分项数、可报价原因/阻断原因。
- 选择规则：仅可报价方案可选；不可报价方案展示原因但不可选。
- 选择结果：方案对象引用；更换客户/房屋后重新加载并清理无效方案。

### 3.4 套餐模板选择器

- 适用场景：套餐报价和套餐基线确认。
- 首屏默认：当前企业可用套餐模板，按适用面积、名称排序。
- 主筛选：面积段、套餐状态、是否可用。
- 搜索：模板名称、适用面积、套餐内容关键词。
- 卡片字段：模板名称、标准面积、套餐价、折扣、分区数、项目数、更新时间。
- 成本权限：仅 BOSS、店长、财务可见成本；设计师只显示销售价和业务内容，不显示成本/毛利。
- 选择结果：套餐模板对象引用；面积参考值可带入，但最终金额仍由服务端汇算。

## 4. 统一机制

所有 App 专用选择器必须复用项目选择器的机制，而不是复制项目业务字段：

- 独立页面或全屏 Sheet，首屏直接展示候选数据；
- 搜索、筛选、分页、加载、空态、失败、无权限、重试；
- 已选对象卡片全宽，展示名称、编号/版本、状态和关键业务事实；
- 支持更换、清除、取消；
- 通过一次性选择通道回传对象引用或清除事件；
- 来源表单消费结果后重新读取依赖数据；
- 服务端保存时再次校验对象归属、状态和权限；
- App/Web 对同一业务对象使用同一筛选语义、业务标签和回传含义。

## 5. 报价表单联动

新建报价表单按以下顺序组织：

```text
客户上下文卡片
-> 房屋上下文卡片（套餐报价必选）
-> 方案上下文卡片（自定义报价必选）
-> 套餐模板上下文卡片（套餐报价必选）
-> 计价面积/折扣
-> 结果预览
-> 生成报价
```

联动规则：

- 更换客户：清空房屋、方案、套餐、报价状态和结果预览；
- 更换房屋：清空方案，重新读取该房屋方案；
- 更换方案：重新计算可报价分项和预估金额；
- 更换套餐：重新按套餐标准面积和规则计算套餐折算金额；
- 客户已确认报价/已转项目：锁定报价并显示原因；
- 所有选择结果提交前由服务端重新校验。

## 8. 验收矩阵

| 类别 | 用例 | 预期 |
| --- | --- | --- |
| 正向 | 新建套餐报价选择客户/房屋/套餐 | 选择后显示全宽业务卡，金额预览刷新 |
| 正向 | 新建自定义报价选择客户/房屋/方案 | 仅可报价方案可选，分项和金额刷新 |
| 反向 | 未选客户直接选房屋/方案 | 阻止并提示先选客户 |
| 反向 | 方案不可报价 | 展示阻断原因，禁止选择 |
| 上下文 | 更换客户 | 房屋、方案、套餐、预览全部失效并重读 |
| 越权 | 其他门店/其他负责人客户 | 服务端不返回或选择后保存被阻断 |
| 大数据 | 超过 100 条客户/套餐 | 服务端分页，不一次性全量加载 |
| 失败恢复 | 选择器接口失败 | 保留原选择并显示重试，不静默清空 |
| 权限 | 设计师查看套餐成本 | 不展示成本/利润字段 |
| 回传 | 连续打开两次选择器 | 不消费旧结果，不误覆盖当前选择 |

## 9. 当前结论

- 问题判断成立，现有报价/方案/套餐选择器不符合 `DEC-021`、`BR-019`、`DEC-023`、`BR-021`。
- 项目选择器可作为统一机制参考，不能直接替代其他业务对象的专用模型。
- 推荐先完成 Phase 1 的 T15/T16 评审和报价主链改造，再向全 App 扩展。

## 10. T15/T16/T17 评审结论

> 裁决依据：用户 2026-10-08 确认“客户、方案、套餐等有业务属性的选择器应像项目选择器一样具备业务特征”；按 `DEC-021`、`BR-019`、`DEC-023`、`BR-021`、`DEC-024`、`BR-022` 形成以下可研发结论。

### 10.1 T15 客户选择器

- 结论：`可研发使用`
- 角色：Designer / Boss / StoreManager / TeamLeader（按既有客户数据范围）
- 首屏：客户列表 + 阶段筛选 + 搜索
- 主筛选：客户阶段、关键词
- 卡片：姓名、手机号、负责人、阶段、小区/地址、最近/下次跟进、量房状态
- 回传：客户引用；更换客户必须使房屋、方案、套餐失效

### 10.2 T15 房屋选择器

- 结论：`可研发使用`
- 前置：必须已选客户
- 主筛选：房屋状态、关键词
- 卡片：小区/楼栋/房号、面积、户型、设计师、最近量房
- 回传：房屋引用；禁止第一条兜底，客户不匹配时拒绝回填

### 10.3 T15 设计方案选择器

- 结论：`可研发使用`
- 前置：客户上下文，可选房屋上下文
- 主筛选：方案状态、可报价、关键词
- 卡片：方案名、编号、版本、状态、房屋、面积、区域数、分项数
- 规则：仅可报价方案可选；不可报价展示阻断原因

### 10.4 T15 套餐模板选择器

- 结论：`可研发使用`
- 主筛选：面积段、关键词
- 卡片：标准面积、套餐价、折扣、分区数、项目数、更新时间
- 权限：成本仅 BOSS/店长/财务可见；设计师不展示成本和利润
- 回传：模板引用；最终金额由服务端汇算

### 10.5 T16 新建报价表单

- 结论：`可研发使用`
- 上下文区：客户、房屋、方案、套餐均使用全宽业务卡
- 短字段区：计价面积、整体折扣
- 结果区：方案分项合计或套餐折算金额，均由服务端最终确认
- 主行动区：生成套餐报价 / 生成自定义报价
- 上下文失效：换客户清空下游；换房屋重读方案；换方案/套餐重算预览

### 10.6 T17 单据化判断

- 新建报价属于稳定单据对象，但当前阶段优先采用“上下文卡片 + 可编辑字段 + 结果区 + 主行动”的轻量单据化表单；
- 不新增重复预览卡；金额预览只展示服务端规则下的待确认值；
- 后续报价编辑/调整页可继续收敛为更完整的单据化主界面。
