## 0. 结论摘要

| 项 | 结论 |
| --- | --- |
| 业务定位 | 签约后、材料采购前的「客户确认事实」记录，不是采购清单 |

## 1. 为什么主材选材要单独做产品设计

### 1.1 业务痛点

报价单通常只约定材料的**类别、品牌、规格范围**。签约后客户还要和设计师现场敲定**颜色、规格、大小**等具体选择。

中小装企的现实做法往往是：

- 微信聊天里发几张图 + 一句话，事后翻不到；
- 现场口头说定，客户过两周反悔，装企没有确认事实；
- 用 Excel 逐材料登记颜色/规格，字段永远建不全，最后没人维护。

结果：材料到场对不上、工地返工、增项扯皮，责任说不清。

### 1.2 现状（2026-09-21 代码事实）

- 签约后到材料采购之间，**没有**任何选材确认事实落库；
- 报价库 `CatalogItem` 只承载材料主数据与价格，**不承载**客户现场选择；
- 材料计划 `MaterialPlan`、采购单 `PurchaseOrder` 与选材**没有**任何引用关系；
- 交接清单规划中 `material_selection` 一项此前无对象承载。

### 1.3 目标

1. 让设计师在客户身边**几十秒内**记录并提交一份选材文本；
2. 让客户确认这个动作**留痕**（确认人 + 确认时间）；
3. 让项目经理、材料员、老板按项目/房屋看到**同一个版本事实**；
4. 变更时**保留历史**，不覆盖已确认内容；
5. 全过程**不动**报价、合同、成本、采购任何数字。

### 1.4 明确不做什么

- ❌ 不做逐材料颜色 / 规格 / 大小结构化字段；
- ❌ 不做选材清单自动转采购单 / 材料计划 / 任务；
- ❌ 不做选材自动改价、改合同、改成本；
- ❌ 不做客户独立账号线上签认（`GAP-005` 未冻结）；
- ❌ 不做「未选材禁止采购」强制门禁（`GAP-005` 未冻结）。

## 2. 业务梳理

### 2.1 业务对象与归属（`OBJ-001`）

```
Customer 客户
  └── Property 房屋（主所属）
        ├── ProjectContract 合同（签约后主归属）
        │     └── Project 项目（创建后建立引用）
        └── MaterialSelection 主材选材记录（按 version 多版本）
              ├── designer      维护设计师
              ├── confirmerName 客户确认人姓名
              ├── confirmedBy   确认操作员工（线上自助 / 设计师代录）
              └── confirmedAt   客户确认时间
```

| 规则 | 口径 |
| --- | --- |
| 唯一归属 | `propertyId` 必填；多房屋客户**必须**显式指定，禁止串房 |
| 合同/项目 | 合同为签约后主归属；项目创建后建立引用，保存时自动带出履约合同 |
| 待补上下文 | 允许先建草稿；**确认环节**要求已绑定合同或项目 |
| 企业归属 | `company/store/team/owner` 由登录员工所属企业 + 房屋归属快照复制，前端不可指定 |

### 2.2 状态与版本

| 状态 | 中文 | 进入方式 | 可编辑 |
| --- | --- | --- | --- |
| `Draft` | 草稿 | 保存草稿 | ✅ 原地保存 |
| `PendingConfirm` | 待客户确认 | 提交客户确认 | ✅ 原地保存 |
| `Confirmed` | 已确认 | 记录客户确认 | ❌ 修改即生成新版本 |

版本规则：

- 同一「企业 + 房屋 + 合同」下 `version` 从 1 递增；
- **未确认**的当前版本允许**原地保存**，避免每次编辑堆积版本；
- **已确认**版本永久保留，需要变更时自动生成 `version + 1` 的新草稿；
- 「当前查看 = 列表第一版（版本号最大）」。

### 2.3 权限与数据范围

| 动作 | 允许角色 | 判定依据 |
| --- | --- | --- |
| 查看 | BOSS、店长、团队负责人、房屋负责人、业务员、设计师、项目经理、履约、财务 | 房屋数据范围（Company / Store / Team / Self）**或**项目参与关系 |
| 维护 / 提交 | 房屋已指派设计师、房屋数据负责人、BOSS、店长、团队负责人、项目经理、履约 | 房屋可见 + 角色具备维护资格 |
| 客户确认 | 同上（代表客户记录确认） | 同上 |
| 拒绝 | 业务员、财务**不可**修改选材事实 | 返回 403 |
| 越权 | 跨企业 / 非数据范围且非项目参与人 | 统一 404，不泄露对象存在性 |

> 前端隐藏入口不构成权限；Provider 继承 `Security`，企业归属与负责人一律服务端覆盖。

### 2.4 金额与成本口径（强约束）

| 维度 | 选材记录的影响 |
| --- | --- |
| 报价 `Quote` 快照 | 不变 |
| 合同 `ProjectContract` 金额 | 不变 |
| 成本 `ProjectCostContext` | 不参与、不改变 |
| 材料计划 `MaterialPlan` | 不生成、不修改 |
| 采购 `PurchaseOrder` / 到货 / 库存 | 不生成、不修改 |
| 应收应付、利润 | 不变 |

**验收口径：保存与确认选材后，上述对象逐字段不变。**

## 3. 真实业务场景

### 场景一：设计师带客户在工地选定主材（主路径）

- **使用人**：设计师；**在场**：客户
- **触发**：客户已签约，设计师约客户看样并现场确认
- **动作**：设计师在 App 打开项目 →「主材选材」→ 按空间录入一段文本 → 提交客户确认 → 客户当场认可 → 填客户姓名 → 记录确认
- **系统下一步**：`PendingConfirm → Confirmed`，写入确认人与确认时间；项目经理/材料员立即可见
- **异常**：客户对某一项犹豫 → 保存草稿不确认，下次现场继续

### 场景二：客户两周后改主意

- **触发**：客户换成另一款砖
- **动作**：设计师打开已确认版本 → 直接修改文本 → 保存
- **系统下一步**：生成 `version + 1` 新草稿，旧版本保持 `Confirmed`；重新提交并记录确认
- **价值**：新旧版本都在，争议时可追溯

### 场景三：项目经理在现场核对到货

- **使用人**：项目经理 / 材料员
- **动作**：项目详情 →「主材选材」→ 查看最新已确认版本
- **系统下一步**：只读展示；采购仍按正式材料计划与采购单流程执行
- **异常**：无选材记录 → 显示空态「尚未创建选材记录」，不阻断开工

### 场景四：老板抽查在跑项目选材进度

- **使用人**：BOSS / 店长
- **动作**：按项目进入选材页，看状态与版本
- **系统下一步**：只在其数据范围内可见；不提供跨企业视图

## 4. 设计原则

### 4.1 现场视角（App）

1. **一屏一动作**：客户就在旁边，主行动是「提交客户确认」，不是配置。
2. **文本优先**：给一个足够大的多行输入框，用示例文案引导「空间 + 材料 + 颜色/规格」的写法，不做表单化。
3. **没有术语**：不出现 `Draft/PendingConfirm/SelectionStatus` 等工程词。

### 4.2 老板视角（Web，待补）

1. 需要**批量**看：哪个项目还没确认选材；
2. 需要**状态一眼可判**：草稿 / 待确认 / 已确认；
3. 需要**不改账**的信任感：明确标注「不改变合同与成本」。

### 4.3 边界视角

- 选材是**确认与协同记录**，任何页面都不应暗示它生成了采购或成本。

## 6. 页面设计（App）

### 6.1 主材选材页 `subpackages/project/pages/selection.vue`

**区域一 · 状态头**

- 左：标题「主材选材」；
- 右：状态标签 `草稿 / 待客户确认 / 已确认`（颜色 token：灰 / 橙 / 绿）；
- 副标题：一句话说明边界 ——「文本按版本保留历史，不改动报价、合同、成本与采购」；
- 元信息：房屋地址、合同编号、「查看项目」跳转。

**区域二 · 选材文本（可编辑）**

- 标题输入（可选）；
- 正文多行输入，placeholder 示例：
  > 按空间记录与客户确认的主材：如「厨房墙砖 浅灰哑光 300x600；主卧地板 原木色多层实木」
- 底部动作：`保存草稿`（次级按钮）、`提交客户确认`（主按钮）。

**区域三 · 客户确认**

- 仅在「未确认 + 具备维护资格」时展示；
- 确认人姓名输入 + `客户已确认` 按钮；
- 已确认时替换为确认结果卡：「已由 {确认人} 确认 / {确认时间}」。

**区域四 · 历史版本**

- 标题「历史版本（N）」；
- 每行：`v{n} · 状态`、设计师 + 创建时间、已确认显示确认人；
- 点击切换查看该版本内容；
- 空态：`尚未创建选材记录`。

### 6.1.1 选材跟进台 `subpackages/project/pages/selection-board.vue`

**用途**：让老板/店长/设计师一眼看到「哪些在跑项目还没确认选材」，并从清单直接进入选材页。

- 顶部摘要卡：`待确认主材选材 N 个项目` + 未创建/草稿/待确认三档计数 + 边界说明（不阻断开工、不改合同与成本）；
- 列表项：项目名 + 项目状态标签、房屋地址与面积、客户与选材设计师、**选材状态标签**、版本与更新时间；
- 每项底部「下一步」条：服务端给出 `nextAction`（发起选材 / 完善文本 / 推动客户确认），点击进入选材页并带 `propertyId + projectId`；
- 只显示**尚未客户确认**的项目，已确认的不出现——这是清单语义，不是全量台账；
- 状态色使用 `STATUS_COLOR`：未创建/草稿→todo 灰、待客户确认→pending 橙；
- 覆盖加载中 / 空态「全部在跑项目已完成选材确认」/ 失败重试；支持下拉刷新。

### 6.2 视觉规范

| 元素 | 规范 |
| --- | --- |
| 容器 | `jz-card` 圆角卡片，卡片间距 20rpx |
| 主色 | 品牌主色（确认态、主按钮、链接） |
| 状态色 | `草稿`=text3 灰、`待客户确认`=warning 橙、`已确认`=success 绿 |
| 正文输入 | 背景 `#F4F7F8`，行高 1.7，字号 28rpx |
| 只读态 | 输入框 disabled + 顶部提示文案，不隐藏内容 |
| 按钮 | 主/次按钮等高，成对排列，禁用态降低透明度 |

## 7. 交互逻辑

### 7.1 状态 × 角色 × 动作矩阵

| 状态 | 设计师/管理者 | 项目经理/履约 | 业务员/财务 | 业主 |
| --- | --- | --- | --- | --- |
| 草稿 | 编辑 / 提交 / 删除输入 | 只读 | 只读 | 不可见 |
| 待客户确认 | 编辑 / 记录确认 | 只读 | 只读 | 不可见 |
| 已确认 | 修改（生成新版本） | 只读 | 只读 | 不可见 |

### 7.2 关键交互流

```text
进入页面
 -> 拉取该房屋全部版本（最新在前）
 -> 默认选中最新版本并回填文本
 -> 设计师修改文本
 -> 保存草稿 / 提交客户确认
 -> 客户现场认可 -> 填客户姓名 -> 客户已确认
 -> 刷新列表（新版本置顶）
```

### 7.3 重复与并发

| 场景 | 处理 |
| --- | --- |
| 重复点击「客户已确认」 | 幂等，直接返回已确认记录，不重写确认人与时间 |
| 两个设计师同时编辑同一房屋 | 采用「后提交生效」，服务端按版本递增，历史版本不丢 |
| 断网后重试提交 | 允许重试；同一未确认版本原地保存，不产生重复版本 |
| 保存时未填正文 | 直接拒绝并提示「请填写主材选材文本」，不落库 |

## 8. 异常态与空态

| 场景 | 表现 | 恢复路径 |
| --- | --- | --- |
| 尚无任何版本 | 空态「尚未创建选材记录」+ 可直接录入 | 填文本后保存 |
| 未绑定合同/项目 | 草稿可保存；点确认时提示「请先绑定合同或项目上下文」 | 从项目进入或补上下文 |
| 无维护资格 | 隐藏编辑与确认区，仅展示文本 | 联系设计师或管理者 |
| 越权访问 | 统一「记录不存在或无权访问」 | 返回 |
| 接口异常 | 顶部提示错误，保留已输入内容不清空 | 重试 |

## 10. 验收标准（供 acceptance lane 设计用例）

**业务闭环**

1. 签约后设计师创建文本 → 提交 → 记录客户确认 → 项目角色可查看；
2. 无结构化颜色/规格/大小字段也能完成全流程；
3. 修改已确认版本 → 生成新版本，旧版本内容与确认信息不变。

**权限**

4. 跨企业访问 → 404；非参与人非范围 → 404；业务员/财务修改 → 403；
5. A 房屋选材不出现在 B 房屋。

**账务**

6. 保存与确认前后，报价、合同金额、成本、材料计划、采购单逐字段不变。

**异常**

7. 空文本 / 无上下文确认 / 重复确认 / 越权详情的表现与 §8 一致。
