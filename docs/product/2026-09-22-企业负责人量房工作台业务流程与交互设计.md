# 装得清 App · 企业负责人量房经营与业务员预约转化工作台设计

> 状态：P0 v1.2 已实现，待 acceptance 独立验收；获客成本明确不进入本轮  
> 范围：微信小程序 BOSS / 店长 / 团队负责人 / 业务员 / 设计师视角的「量房经营与预约转化工作台」；以 BOSS 经营和业务员预约转化为主，不修改现有生产实现  
> 日期：2026-09-22  
> 业务依据：`SCN-001`、`BR-001`、`CAP-002`、`DEC-002`  
> 参考模式：企业负责人方案设计、报价谈单、合同签约工作台；Web `DesignerMeasureWorkbenchView` / `MeasurementWorkbenchView`

---

## 0. 结论摘要

量房工作台不是一个更大的“录入量房表单”，而是一张**以房屋为单位、围绕业务员预约、设计指派、现场执行、量房完成、设计接手五个控制点组织的工作台**。

其中，“已预约量房”是销售转化的核心里程碑：它不证明客户已签约，但表示客户已经投入一次真实的上门沟通成本，是装企判断获客质量、业务员推进质量和后续设计商机的关键节点。

企业负责人打开量房工作台，必须立刻回答：

1. 有多少客户已经预约量房，预约率是多少？
2. 哪些业务员有客户但没有推进预约，谁的转化最弱？
3. 今日、未来和逾期预约分别有哪些，谁负责推进？
4. 哪些房屋已完成量房但还没有指定设计责任人？
5. 哪些完成量房超过 48 小时仍未进入设计，正在沉积商机？
6. 客户来源不同，预约率和量房完成率有什么差异，获客问题出在哪里？

页面继续复用昨日工作台模式：

```text
经营结论 Hero
-> 风险指标
-> 左侧业务员分组（可切换设计师视角）
-> 右侧客户/房屋卡片
-> 卡片展示当前事实 + 责任 + 卡点 + 下一步
-> 进入量房详情或执行动作
```

量房工作台的核心业务对象是 **Property + Measure**，经营分析主维度是 **业务员 + 客户来源**。一个客户多套房时，每套房必须有独立预约、独立设计责任人、独立执行人和独立完成事实；客户级设计责任人继续保持客户级语义。

## 1. 为什么要做量房工作台

### 1.1 当前产品状态

后端已有：

- `Measure`：绑定企业、客户、房屋、设计责任人、实际执行人、预约/实际时间、状态和现场资料；
- `MeasureStatus`：`Scheduled / Completed / Cancelled`；
- `PropertyStatus`：`PendingMeasure / Measuring / Measured / Designing / ...`；
- `property/measure/save`、`property/measure/info`、`property/measure/page`；
- `customer/customer/measure`：约定量房；
- `customer/customer/handoff`：指定或更换设计师；
- 量房完成后只能由指定设计师执行，重复完成幂等。

App 目前只有：

- 客户详情中的“约定量房”；
- 客户详情中的“录入量房记录”；
- 量房记录只强调“谁在什么时候完成了量房”这一事实。

Web 已有：

- 设计师量房行程视图；
- 按逾期 / 今日 / 未来分组的行程；
- 客户信息、量房资料和设计关注点参考；
- 量房录入抽屉。

但 App 负责人端没有一张真正的量房经营工作台：看不到全局待预约、预约率、业务员推进质量、逾期、未指派、完成未交设计和客户来源转化差异。

### 1.2 企业负责人的真实损失

- 只看客户数和签约数，无法判断业务员有没有把客户推进到“预约量房”这个关键里程碑；
- 不知道客户来源之间的预约率、完成率和设计接手率，获客问题被最终签约结果掩盖；
- 不知道哪个业务员有大量客户但没有预约量房，工作质量只能靠主观管理；
- 无法计算每获取一个有效预约、完成量房或进入设计的获客成本；

- 客户约了今天量房，负责人不知道谁去、有没有人去；
- 量房时间过了没有人改约，客户流失后才发现；
- 客户已完成量房，但没有指定设计责任人，后续设计、报价全部停滞；
- 设计师完成了量房，但企业负责人看不到完成质量、照片和交接状态；
- 多个设计师工作负荷不均，负责人无法按数据调度；
- 多套房客户被客户级 `measureAt` 投影污染，导致“第一套房已量房、第二套房显示已量房”的错误判断风险。

### 1.3 设计目标

在不改变现有量房事实口径、不把量房变成财务动作的前提下：

- 让 BOSS 一屏看清量房供给、风险和下一步；
- 让店长 / 团队负责人能在自己的数据范围内调度；
- 让设计师直接处理“今天要去的房屋”，而不是去客户详情中寻找；
- 让业务员看到自己负责客户从建档、跟进到预约量房、完成量房和设计接手的完整转化；
- 让每次量房都有唯一责任、真实时间和完整现场证据；
- 让量房完成后自然进入设计，而不是靠线下提醒；
- 让经营者能按客户来源和业务员观察获客质量、转化漏斗和获客成本。

## 2. 业务事实源与不变量

### 2.1 对象链

```text
Customer 客户
  └── Property 房屋（一客多房）
        └── Measure 量房任务/事实
              ├── designer：设计责任人
              ├── executor：实际执行人
              ├── measureTime：兼容字段
              ├── sitePhotos：现场照片
              └── structureImages / attachments：可选现场资料
```

### 2.2 必须坚持的不变量

1. **房屋是量房唯一承载对象**：不能用客户第一套房屋兜底；
2. **量房前必须有房屋档案**：不能在客户地址上直接量房；
3. **量房动作不产生金额、成本、应收、应付、结算或利润**；
4. **量房完成只形成量房事实**：不自动完成设计、不自动推进报价、不自动签约；
5. **设计责任人与实际执行人分离**：Boss 可将设计责任指派给设计师，但实际到场执行人单独记录；
6. **完成量房必须由指定设计师执行**：业务员、其他设计师、店长和普通负责人不得越过指定设计师代完成；
7. **重复提交幂等**：同一房屋重复完成不覆盖原量房时间、执行人、设计责任人和附件；
8. **服务端是状态权威**：App 只提交动作，动作成功后重新拉取事实。

### 2.3 当前数据字段的实际限制

当前 `Measure` 只有一个 `measureTime`：

```text
Scheduled  -> measureTime = 计划上门时间
Completed  -> 同一字段被覆盖为实际完成时间
```

这会导致：

- 无法计算“计划准时率 / 平均延迟”；
- 改约后丢失原计划时间；
- 无法区分客户预约迟到和设计师执行迟到；
- 负责人只能看到一种“时间”，无法判断风险来源。

**建议冻结的数据模型：**

```text
scheduledAt  计划上门时间，Scheduled 时写入，改约时更新
completedAt  实际完成时间，Completed 时写入，不改写 scheduledAt
measureTime  兼容投影：Completed 时=completedAt，Scheduled 时=scheduledAt
```

P0 可以在不破坏旧接口的情况下先兼容读取；新增字段需 migration、历史数据回填和双写验证后再作为唯一排程依据。

## 4. 真实业务场景

### 场景一：老板查看业务员的预约量房转化

- 使用人：企业负责人。
- 触发事件：本月新增客户不少，但预约量房数量偏低，老板怀疑获客或业务员推进有问题。
- 当前动作：打开量房工作台，默认按业务员分组查看客户漏斗。
- 系统下一步：显示每位业务员的负责客户数、未预约客户数、预约量房数、预约率、完成量房数、完成率、逾期数和交设计数；客户来源同时展示视频、转介绍、到店等渠道的预约率差异。
- 异常处理：来源、跟进或设计关联数据缺失时显示“暂不可判断”，不能按 0 参与率计算。

### 场景二：业务员每天推进未预约客户

- 使用人：家装顾问/业务员。
- 触发事件：早上打开工作台，准备安排今天要联系的客户。
- 当前动作：进入“我的预约转化”，先看未预约客户，再按客户等级、最近跟进和停留时间处理。
- 系统下一步：卡片提供“继续跟进、约定量房、查看客户 360”；预约成功后客户进入“已预约待完成”，并同步进入 BOSS 的业务员和来源转化看板。
- 异常处理：没有房屋档案时先引导建档；接口失败保留客户记录和重试入口。

### 场景三：老板查看今天有几户要量房

- 使用人：企业负责人。
- 触发事件：早上进入公司，准备安排当天设计师工作。
- 当前动作：打开 App → 工作台 → 量房工作台 → 切换“设计师执行”视图。
- 系统下一步：显示今日量房、逾期未完成、待指派设计、最近完成；时间轴展示今天上午/下午的具体预约，并按设计师分组。
- 异常处理：接口失败显示“量房状态暂不可确认”；不能把空数组伪装成“今天没有量房”。

### 场景四：预约超过 4 小时未完成，负责人介入

- 使用人：企业负责人。
- 触发事件：房屋预约超过 4 小时仍处于 `Scheduled`，没有完成量房。
- 当前动作：在“已逾期”分组查看卡片，看到客户来源、业务员、预约时间、设计责任人、执行人。
- 系统下一步：显示“预约已超过 4 小时未完成”，提供联系客户、催办业务员/设计师、改约、查看客户 360。
- 异常处理：改约更新同一房屋的预约事实，不新增第二条有效预约；重复提交服务端幂等返回已有事实。

### 场景五：客户完成量房，但超过 48 小时没有进入设计

- 使用人：企业负责人。
- 触发事件：量房完成超过 48 小时，设计侧仍没有诉求或方案。
- 当前动作：切到“待交设计”筛选，查看完成时间、理论设计和停留时长。
- 系统下一步：进入设计工作台或客户设计页，提醒设计责任人补录诉求和推进方案。
- 异常处理：设计接口失败时显示“设计状态暂不可确认”，不把量房完成误报成设计已开始。

### 场景六：多套房客户分别安排量房

- 使用人：店长或团队负责人。
- 触发事件：同一客户有两套房屋，A 房先量，B 房后量。
- 当前动作：在客户卡片下展开房屋，分别处理 A/B 房预约。
- 系统下一步：每套房独立显示 `Measure.scheduledAt`、责任人、执行人和状态；不能在客户级用一个 `measureAt` 覆盖所有房屋。
- 异常处理：房屋未建档先引导建档；跨客户或跨企业房屋 ID 返回 404。

## 5. 工作台业务模型

### 5.1 页面主对象

`MeasureWorkbenchItem` 以 **Measure + Property** 为主投影：

```text
measureId / propertyId / custId
customerName / telNo / customerGrade
source / sourceName / owner / marketer
community / building / roomNo / address / area / layout
designer / executor
scheduledAt / completedAt
measureStatus / rescheduleCount
sitePhotoCount / structureImageCount / attachmentCount
derivedState / riskLevel
handoffState / handoffStartedAt
nextAction / leadTimeHours / stayHours
```

### 5.2 工作台派生状态

不新增不可维护的前端状态机，由服务端按 Measure + 时间 + 设计交接事实推导：

| 派生状态 | 判断 | UI 文案 | 默认动作 |
| --- | --- | --- | --- |
| `NotScheduled` | 有效客户/房屋尚未形成首次预约 | 未预约量房 | 业务员继续跟进、约定量房 |
| `Unassigned` | `Scheduled` 且无设计责任人 | 已预约·待指派 | 指派客户级设计责任人 |
| `Scheduled` | `Scheduled` 且未超过 4h | 已预约·待上门 | 联系、催办、改约 |
| `Overdue` | `Scheduled` 且 `当前时间 > scheduledAt + 4h` | 预约逾期 | 联系、催办、改约 |
| `CompletedPendingHandoff` | `Completed` 且超过 48h 无设计诉求/方案 | 量房完成·待交设计 | 去设计、提醒设计责任人 |
| `DesignStarted` | `Completed` 且设计诉求/方案已形成 | 已交设计 | 查看设计 |
| `Cancelled` | `Cancelled` | 已取消 | P0 只读；P1 补取消原因 |
| `Unknown` | 关联接口失败 | 状态暂不可确认 | 重试 |

### 5.3 风险等级

| 等级 | 条件 |
| --- | --- |
| `Danger` | 预约超过 4h 未完成；已预约但无设计责任人；完成超过 48h 未交设计 |
| `Warning` | 未来 24h 内预约但没有执行人；改约次数超过 2 次；业务员大量客户未预约 |
| `Normal` | 正常待执行、已完成并已交设计 |
| `Unknown` | 量房、客户、跟进或设计关联加载失败 |

### 5.4 预约量房经营口径

#### 5.4.1 预约里程碑

“预约量房”以**同一房屋首次形成有效 `Scheduled` Measure**为里程碑：

- 同一房屋首次预约只计一次；
- 后续改约只增加改约次数，不重复增加预约量房数；
- 多套房客户按房屋分别计数；
- 预约是否已有设计责任人不影响“预约量房数”，但影响“可执行/待指派”状态；
- 预约时间以房屋级 `Measure.scheduledAt` 为准。

#### 5.4.2 经营漏斗

```text
新增客户/来源线索
  -> 有效跟进客户
  -> 已预约量房客户
  -> 已完成量房客户
  -> 已交设计客户
```

预约量房是业务员推进结果，不等于签约、收入、报价或项目成立。

#### 5.4.3 核心指标

| 指标 | 推荐公式 | 口径说明 |
| --- | --- | --- |
| 预约量房数 | 首次 `Scheduled` 的房屋去重数 | 按首次预约时间归集 |
| 预约率 | 预约量房数 / 同期有效跟进客户数 | 可按业务员、来源、门店拆分 |
| 完成量房数 | `Completed` 的房屋去重数 | 同一房屋只计一次 |
| 预约完成率 | 完成量房数 / 同期预约量房数 | 使用同一预约队列 |
| 逾期预约数 | `Scheduled` 且超过 `scheduledAt + 4h` | 经营者介入依据 |
| 逾期率 | 逾期预约数 / 同期预约量房数 | 反映预约推进和现场执行质量 |
| 交设计数 | 完成量房后已形成设计诉求/方案的房屋数 | 以设计域事实为准 |
| 交接率 | 交设计数 / 完成量房数 | 反映量房后的商机承接 |
| 平均预约时长 | 首次预约时间 - 客户建档/首次跟进时间 | 评价业务员推进效率 |
| 平均完成时长 | `completedAt - scheduledAt` | 依赖预约/完成时间分离 |
| 改约次数 | 同一房屋预约时间变更次数 | 识别客户不稳定或排期问题 |
| 获客成本 | 渠道/活动获客费用 / 约定分母 | 成本数据缺失时返回 `null` |

#### 5.4.4 业务员经营维度

业务员是 P0 的第一分析维度，每个业务员至少展示：

- 负责客户数；
- 未预约客户数；
- 预约量房数、预约率；
- 完成量房数、预约完成率；
- 4h 逾期数、逾期率；
- 平均预约时长；
- 完成量房后 48h 待交设计数；
- 客户来源分布及其预约率。

#### 5.4.5 获客成本边界

当前系统有 `Customer.source`，但没有广告费用、活动归因、渠道分摊和成本证据。系统不得用客户数推算获客成本。

后续建议新增独立成本事实：

```text
period / source or campaign / spendAmount / currency /
attributionRule / owner / evidence
```

在成本事实完整前，页面只能显示“获客成本未录入”，不能显示 0、伪造成本或推断利润。

### 7.3 量房详情页

结构：

1. Hero 结论：当前状态、风险、下一步；
2. 客户/房屋摘要；
3. 预约事实：`scheduledAt`、改约次数、预约创建人；
4. 责任事实：客户级设计责任人、实际执行人；
5. 执行事实：`completedAt`、现场照片数量、附件数量；
6. 设计交接：诉求/方案是否形成、最近更新时间；
7. 时间线：建档 → 跟进 → 预约 → 改约 → 完成 → 设计接手；
8. 底部动作条按状态变化。

### 7.4 执行量房页

设计师使用，BOSS 只有在被指派为客户设计责任人且服务端允许时才能完成。

必填：

- 实际量房日期时间；
- 至少 1 张现场照片；
- 房屋属于当前客户且已建档。

可选：

- 结构图、附件、备注。

规则：

- 必须有设计责任人；
- 只能由指定设计师本人完成；
- 重复完成幂等，不覆盖 `scheduledAt`、`completedAt`、执行人和附件；
- 完成后只把房屋更新为 `Measured`，并写 `latestMeasureAt`；
- 不自动完成设计，不自动推进报价或项目。

弱网：

- 上传失败不退出；
- 保留照片和备注；
- 显示“有未提交量房草稿”；
- 重试使用幂等请求。

### 7.5 指派设计责任人

打开设计师选择半屏：

- 搜索姓名、门店、团队；
- 展示客户级当前设计责任人和候选设计师；
- 展示设计师当前量房负荷、4h 逾期数、今日行程；
- 指派后同步更新未完成 Measure 的设计责任人；
- 明确提示“客户级指派会影响该客户名下未完成设计任务”。

### 7.6 改约 / 取消

改约：

- 更新同一房屋当前 `Scheduled` 记录；
- 更新 `scheduledAt`；
- 保留历史计划时间或改约次数；
- 重新计算 4h 逾期、今日行程和业务员统计。

取消：

- P0 展示 `Cancelled`，不改变客户级设计责任；
- P1 增加取消原因、取消人和失联/爽约分类。

### 7.7 交互总流程

```text
BOSS 打开量房工作台
  -> 查看预约量房、预约率、完成率、4h 逾期、48h 待交设计
  -> 默认按业务员分组
  -> 查看未预约客户池
  -> 业务员继续跟进并预约量房
  -> 预约生成房屋级 Measure.scheduledAt
  -> 待指派：指定客户级设计责任人
  -> 待上门：设计师执行并上传实际时间+现场照片
  -> 完成：房屋进入 Measured，进入设计交接观察
  -> 48h 未交设计：提示负责人/业务员跟进
  -> 设计诉求/方案形成：标记已交设计
```

所有动作成功后重新拉取服务端事实，不以本地布尔值伪造状态。
