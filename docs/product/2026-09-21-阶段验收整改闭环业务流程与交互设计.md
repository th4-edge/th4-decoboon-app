## 0. 结论摘要

| 项 | 结论 |
| --- | --- |
| 整改对象 | **阶段级**（`ProjectStage`），不建任务级/分项级整改单 |
| 不合格后归属 | **复用同一阶段与同一张验收单**，不新建单据 |
| 循环次数 | **允许多次循环，不设上限** |
| 记录方式 | **原验收记录保留，追加结论**（append-only 轮次） |
| 账务边界 | **只做质量事实，不碰账**——不改合同、成本、应收应付、利润 |
| 主端选择 | App 承担现场提交与整改留证；Web 承担复核与督办 |
| 与开工门禁 | 阶段整改**不阻塞其他阶段**推进；但该阶段未验收通过不能进入下一关键节点 |

## 1. 为什么整改闭环要单独做产品设计

### 1.1 业务痛点

家装现场几乎不存在「一次验收就过」的阶段。真实情况是：

- 业主到场挑出问题（瓷砖空鼓、收口不严、开关高度不对）；
- 项目经理口头答应「明天改」，改完没人记录；
- 业主第二次来看，问题改没改、改了几处、谁确认的，全靠记忆。

**结果**：阶段迟迟结不掉，尾款结不掉，出了问题装企举证困难。

### 1.2 现状（2026-09-21 代码事实）

`Acceptance`（`db_acceptance`）字段：`project`、`property`、`stage`、`submittedBy`、`status(Pending/Confirmed/Rejected)`、`conclusion`、`issues[]`、`evidenceUrls[]`、`rectificationOwner`、`rectificationDueDate`、`confirmedAt`、`confirmedBy`。

- 已有：阶段级验收单、问题清单、整改责任人与截止日期、业主确认/驳回（`project/acceptance/update` 仅业主本人可确认，员工不得代录）。
- **缺失**：
  - 没有「第几轮」事实，驳回后重新提交会**覆盖**上一轮结论；
  - 没有整改动作记录（整改说明、整改后照片）；
  - 没有「一次通过率」「平均整改轮次」的口径基础。

类注释写「驳回时保留原因并允许整改后重新提交」，**与实现不一致**——本稿即为修正该缺口。

### 1.3 目标

1. 项目经理驳回后**当场登记整改要求**（问题、责任人、截止日期）；
2. 整改完成**再次提交**时，系统自动形成**新一轮**，历史轮次全部保留；
3. 业主每次确认/驳回都**追加结论**，不覆盖；
4. 店长/BOSS 能一眼看出「这个阶段卡在整改第几轮、谁是责任人、逾期没」；
5. 全过程**不动任何金额**。

### 1.4 明确不做什么

- ❌ 不做任务级/分项级整改单（整改对象只有阶段）；
- ❌ 不做整改单独立主键与独立状态机（复用阶段与验收单）；
- ❌ 不做整改次数上限、不做超过 N 次自动升级审批；
- ❌ 不做返工成本计入项目成本、不做减项、不做违约金；
- ❌ 不改付款计划、应收应付、结算与利润。

## 2. 业务梳理

### 2.1 业务对象与归属

```
Project 项目
  └── ProjectStage 施工阶段（整改的唯一归属层级）
        └── Acceptance 阶段验收单（1 阶段 1 张，长期存在）
              └── AcceptanceRound 验收轮次（append-only，不限条数）
                    ├── roundNo            第几轮
                    ├── submittedBy/At     提交人与提交时间
                    ├── rectificationNote  本轮针对上一轮问题的整改说明
                    ├── rectificationEvidenceUrls 整改后照片
                    ├── issues[] 本轮仍是的问题（由业主确认/驳回时填写）
                    ├── result             本轮结论：待确认 / 通过 / 驳回
                    ├── conclusion         本轮结论文字
                    ├── confirmedBy/At     业主确认人与时间
                    └── rectificationOwner/DueDate 驳回时给下一轮的责任人与截止
```

| 规则 | 口径 |
| --- | --- |
| 唯一归属 | 阶段级；`stage_id` 必填，不跨阶段 |
| 单据复用 | 同一阶段**始终只有一张** `Acceptance`；轮次是子记录 |
| 追加不覆盖 | 每轮结论一旦写入**不可修改**；纠错只能发起新一轮 |
| 循环次数 | 无上限，`roundNo` 自然递增 |
| 首轮 | 阶段首次提交验收即第 1 轮（无整改说明） |

### 2.2 状态与轮次模型

**验收单状态（`AcceptStatus`，保持三值，表示「当前轮次」结果）**

| 状态 | 中文 | 含义 |
| --- | --- | --- |
| `Pending` | 待确认 | 当前轮已提交，等业主结论 |
| `Confirmed` | 已确认 | 当前轮通过，阶段可结 |
| `Rejected` | 整改中 | 当前轮驳回，等项目经理整改后再次提交 |

**轮次流转（不限循环）**

```text
第 N 轮提交（Pending）
   ├── 业主确认 → Confirmed（闭环结束，阶段验收通过）
   └── 业主驳回 → Rejected（登记问题 + 整改责任人 + 截止日期）
            ↓ 现场整改
        第 N+1 轮提交（含整改说明与照片，Pending）
            ├── 业主确认 → Confirmed
            └── 业主驳回 → Rejected ……（继续循环）
```

**关键不变量**

1. 同一阶段任何时刻最多 1 个 `Pending` 轮次；
2. `Confirmed` 之后不得再提交新轮次（防脏数据）；
3. 历史轮次的 `result/conclusion/confirmedAt` 不可修改；
4. `roundNo = 历史轮次数 + 1`，不允许跳号。

### 2.3 权限与数据范围

| 动作 | 允许角色 | 判定依据 |
| --- | --- | --- |
| 提交验收 / 整改反馈 | 项目经理、履约专员、设计师（项目参与关系） | 项目数据范围 + 项目参与 |
| 登记整改责任人与截止日期 | 项目经理、履约专员 | 同上 |
| 业主确认 / 驳回 | **仅业主本人**（授权会话） | `project/acceptance/update` 既有口径，员工不得代录 |
| 查看 | BOSS、店长、团队负责人、项目参与人、业主 | 项目数据范围或参与关系 |
| 越权 | 跨企业、非参与人、非范围 | 统一 404，不泄露对象存在性 |

### 2.4 金额与成本口径（强约束）

| 维度 | 整改循环的影响 |
| --- | --- |
| 报价 / 合同金额 | 不变 |
| 项目成本 / 实际成本 | **不变**（返工成本不走系统，仍由线下承担） |
| 应收 / 应付 / 结算 / 利润 | 不变 |
| 允许产生的派生指标 | 整改轮次数、整改时长、一次通过率（**只读统计，不写账**） |

> 若后续业务要求返工成本入账，必须另行立项并建立 `GAP-*`，不得在本闭环内扩展。

## 3. 真实业务场景

### 场景一：业主第一次验收挑出问题

- **使用人**：项目经理（在场）、业主
- **触发**：阶段施工任务全部完成，提交验收
- **动作**：PM 在 App 提交验收（结论 + 现场照片）；业主到场驳回，勾选/填写问题清单，指定整改责任人与截止日期
- **系统下一步**：形成第 1 轮 `Rejected`，阶段标签显示「整改中 · 第 1 轮」，PM 工作台出现整改待办
- **异常**：业主不在场 → 验收保持 `Pending`，PM 不能自行判定通过

### 场景二：整改后第二次验收通过

- **动作**：PM 在 App 打开同一验收单 →「提交复验」，填写**整改说明**并上传整改后照片 → 业主到场确认
- **系统下一步**：形成第 2 轮 `Confirmed`，阶段验收通过，历史第 1 轮问题清单一字不动
- **价值**：一条时间线说清「改了什么、谁确认的、原来什么问题」

### 场景三：改了三次还没过（不限循环）

- **动作**：第 2、3 轮均被驳回
- **系统下一步**：轮次继续追加，`roundNo=4` 已提交待确认；店长视图显示「整改中 · 第 3 轮 · 已逾期 2 天」
- **边界**：系统**不**自动升级、**不**限制次数、**不**改合同

### 场景四：店长督办与老板抽查

- **使用人**：店长、BOSS
- **动作**：按项目/门店查看「整改中的阶段」清单，看轮次、责任人、是否逾期
- **系统下一步**：只读；点进去可看完整轮次时间线
- **异常**：无整改项目 → 空态「当前没有整改中的阶段」

## 4. 设计原则

### 4.1 现场视角（App）

1. **一屏看完历史**：默认展示时间线，最近一轮在最上面；
2. **提交复验必带整改说明**：否则业主看不出改了什么；
3. **不让 PM 判断「过没过」**：结果只能由业主写。

### 4.2 管理视角（App/Web）

1. 管理页只回答三个问题：**哪几个阶段卡在整改、第几轮、超没超期**；
2. 轮次数是质量信号，不是考核工具——文案避免评价性表述。

### 4.3 边界视角

- 任何页面都不得出现「整改费」「扣款」「返工成本」等字段或暗示。


## 6. 页面设计（App）

### 6.1 阶段验收页（改造现有 `accept/edit.vue`）

**区域一 · 状态头**

- 状态标签：`待确认`（pending 橙）/ `已确认`（done 绿）/ `整改中 · 第 N 轮`（blocked 红）
- 副标题：阶段名 + 第几轮 + 提交时间

**区域二 · 当前轮操作**

- `Pending`：不可编辑，提示「等待业主确认」；
- `Rejected`：显示整改要求卡（问题清单、责任人、截止日期、剩余/逾期天数）+ 主按钮「提交复验」；
- `Confirmed`：不显示提交入口。

**区域三 · 提交复验表单**（`Rejected` 时）

- 整改说明（必填，多行）；
- 整改后照片（必填 ≥1 张）；
- 补充说明（可选）。

**区域四 · 轮次时间线**

- 每轮一行：`第 N 轮` + 结果标签 + 提交人/时间 + 结论文字 + 缩略图；
- 本轮若为驳回，展示问题清单与整改责任人；
- 点击展开该轮证据图；
- 顺序：最新在最上，只读。

### 6.2 整改跟进页（新增，管理视角）

- 顶部摘要：`整改中的阶段 N 个`（含逾期 M 个）；
- 列表项：项目名 + 阶段名、`整改中 · 第 N 轮`、整改责任人、截止日期与剩余/逾期、最近结论摘要；
- 点击进入阶段验收页；
- 覆盖加载中 / 空态 / 失败重试；支持下拉刷新。

### 6.3 视觉与状态色

| 元素 | 规范 |
| --- | --- |
| 状态标签 | 复用 `STATUS_COLOR`：`待确认`→pending、`已确认`→done、`整改中`→blocked |
| 轮次徽标 | 中性灰 `STATUS_COLOR.todo`，形如 `第 2 轮` |
| 逾期 | 文字 + `STATUS_COLOR.blocked`，禁止只用颜色 |
| 时间线 | 左侧竖线 + 圆点，圆点色随该轮结果 |

## 7. 交互逻辑

### 7.1 状态 × 角色 × 动作矩阵

| 当前轮状态 | 项目经理/履约 | 业主 | 店长/BOSS |
| --- | --- | --- | --- |
| 待确认 | 只读，等待 | 确认 / 驳回（必填问题清单） | 只读 |
| 整改中（第 N 轮） | 登记/调整整改责任人与截止、提交复验 | 不可操作 | 只读 + 督办 |
| 已确认 | 只读 | 只读 | 只读 |

### 7.2 关键交互流

```text
PM 提交验收（第 1 轮）
 -> 业主驳回：勾选问题 + 指定整改责任人 + 截止日期
 -> 形成第 N 轮 Rejected，PM 收到整改待办
 -> PM 现场整改，上传整改说明与照片，提交复验
 -> 形成第 N+1 轮 Pending
 -> 业主确认 -> 第 N+1 轮 Confirmed -> 阶段验收通过
```

### 7.3 重复与并发

| 场景 | 处理 |
| --- | --- |
| 重复点击「提交复验」 | 幂等：同一阶段已有 `Pending` 轮次时直接返回该轮次，不新增 |
| 业主重复确认 | 幂等：已 `Confirmed` 直接返回，不重写确认人/时间 |
| PM 与履约同时提交复验 | 服务端按「同阶段最多一个 Pending」串行化，后到者返回已有轮次 |
| 已通过后再次提交 | 拒绝并提示「该阶段验收已通过」 |

## 8. 异常态与空态

| 场景 | 表现 | 恢复路径 |
| --- | --- | --- |
| 尚无验收单 | 空态「尚未提交验收」，提供「提交验收」 | 提交第 1 轮 |
| 待业主确认 | 提示「已提交，等待业主确认」，禁用提交 | 等待或线下沟通 |
| 整改中 | 高亮整改要求与截止日期 | 提交复验 |
| 已通过 | 展示通过结论与轮次时间线 | — |
| 无权限 | 「当前身份无验收操作权限」 | — |
| 接口失败 | 保留已填写的整改说明与已选照片 | 重试 |

## 10. 验收标准（供 acceptance lane 设计用例）

**正向**

1. 第 1 轮提交 → 业主驳回 → 第 2 轮提交复验 → 业主确认，阶段通过；
2. 时间线完整展示全部轮次，历史轮次内容一字不变。

**循环**

3. 连续驳回 3 次后第 4 轮通过，轮次为 4 且不跳号；
4. 循环次数无上限，不出现自动升级或锁定。

**追加不覆盖**

5. 第 2 轮通过后，第 1 轮的 `conclusion`、`issues`、`confirmedAt` 与原来一致。

**权限**

6. 员工调用 `project/acceptance/update` 确认/驳回 → 403；
7. 跨企业、非参与人查看 → 404。

**账务**

8. 整改循环前后，合同金额、项目成本、应收应付、结算与利润逐字段不变。

**异常**

9. 同阶段并发提交复验只产生一个 `Pending` 轮次；
10. 已通过后再次提交被拒绝。
